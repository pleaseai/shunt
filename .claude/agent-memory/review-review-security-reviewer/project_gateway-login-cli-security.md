`src/auth/gateway/{login,auth,store,launch}.rs` (client side of `[server.gateway]`, RFC 8628 device flow, session cached at `$SHUNT_GATEWAY_SESSION_FILE` else `~/.shunt/gateway/session.json`).

**Verified safe** (do not re-flag without new evidence):
- Session file is born-private: `shared::write_account_file` -> `create_private_dir` (0700) + `atomic_file::write_private` (`create_new` + `mode(0o600)` on the *temp* file too). No chmod-after-write window.
- `GatewaySession`, `TokenResponse`, `DeviceCode` all have hand-written redacting `Debug`; re-verified field-by-field against each struct in round 2. No `derive(Debug)` on any of them; no token reaches logs, errors, or a panic payload. `Discovery` does derive `Debug` and *is* printed in a panic message (`auth.rs:417`) but holds only endpoint URLs.
- `shunt gateway token` prints only the token on stdout (integration-tested in `tests/gateway_cli.rs`, including the failure path). Every warning goes to stderr — including `warn_on_unknown_protocol_version`, which is on the helper path.
- All credential POSTs use `shared::token_refresh_client()` (redirect policy: https-or-loopback only).
- `launch.rs` builds `apiKeyHelper` with proper POSIX single-quote escaping and the `--settings` doc via `serde_json`, not `format!`. The gateway URL never reaches `shell_quote` — it goes into the `env` object and is serde-escaped, so quotes/newlines/JSON metacharacters cannot break the document.
- **No argv smuggling past `reject_swallowed_config`.** Probed against the built binary in all four positions (before the subcommand, leading the forwarded args, non-leading, after `--`), plus the `--config=foo` equals-form. `--config` is the sole `global = true` arg on `Cli`; `--check` is declared without it; there is no `--version`. `claude_args` forwards verbatim with no reorder/drop/reinterpret. Do not re-raise without a concrete argv.
- `interval` from the device response cannot busy-spin or overrun: `positive_secs` rejects 0, `.max(MIN_INTERVAL_SECS)`, and every sleep is `remaining.min(interval)`.

**Closed by `ac7d7e8`** ("fix(gateway-cli): vet gateway-chosen URLs and cover the refresh lock") — re-verified in round 2, do not re-report:
- `browser_open_refusal` (`login.rs:178-189`) gates the verification URL's scheme to http/https before it reaches the OS handler, and it gates `prompt_url` — the string actually opened — not `verification_uri` unconditionally.
- `parse_discovery` (`auth.rs:130-158`) applies `shared::is_safe_refresh_url` to **both** endpoints. Field evaluation order is safe (device endpoint checked first, `Unsafe` short-circuits ahead of the 404 fallback).
- Body reads that die after the headers retry instead of `unwrap_or_default()`-ing; the counter logic is sound and `last_transport_error` is cleared on any complete response so the timeout message stays honest.
- `flock` coverage in `store.rs`/`auth.rs` (the tests, not the lock itself — see residual 1 for the hazard the pre-existing lock carries).
- Non-UTF-8 executable path errors instead of being lossily mangled into an apiKeyHelper.

**Residual gaps as of round 2 — all three queued for fix:**
1. **Refresh lock held across two untimed network round-trips.** `resolve_token_at` (`auth.rs:276-296`) takes an unconditional blocking `LOCK_EX` (`store.rs:204`, no `LOCK_NB`, no timeout) and then does `discover()` **and** `refresh()` inside it, while `token_refresh_client()` sets neither `.timeout()` nor `.connect_timeout()`. A gateway that accepts the connection and never responds hangs the holder forever, and every other session's `apiKeyHelper` then blocks forever in `lock_blocking` — not failing, just hanging with no output. One unreachable gateway wedges every Claude Code session on the machine. NOT introduced by the round-1 fix — the lock is from the original implementation; ac7d7e8 only added the tests that had been missing ("Cover the file lock, which had none"). Look in the feature commits, not in ac7d7e8.
2. **`expires_at_ms` has no upper clamp** (`auth.rs:237-250`, `is_valid_at` at `auth.rs:252-258`). `saturating_add` is correct against overflow but unbounded upward, so a gateway emitting `expires_in` in **milliseconds** (a plausible plain bug, not just hostility) caches a dead token as valid ~forever. Symptom: every request 401s, Claude Code re-runs the helper on the 401, gets the identical dead token back, loops. Recoverable only by deleting `session.json` by hand.
3. **The apiKeyHelper output contract is enforced only in the test file.** `tests/gateway_cli.rs:11-23` spells out Claude Code 2.1.234's validator (printable ASCII `!`–`~`, ≤16384 chars) but no production code checks it: `parse_token_response` only rejects empty, `parse_session` only `trim()`s the ends. Verified empirically — an `accessToken` holding `\n` prints two lines on stdout, which Claude Code rejects wholesale with no useful diagnostic.
4. (Carried from round 1, still open, queued.) `normalize_gateway_url` (`login.rs:144-167`) warns about plaintext http **only at login**; later `gateway token` refreshes over the stored `http://` URL are silent.

**Deferred with reason — do NOT re-raise at IMPORTANT severity:**
- *"Discovery endpoints are not bound to the gateway's origin"* (`parse_discovery` vets transport only; `issuer` is never read; RFC 8414 §3.3 check absent; a test at `auth.rs:371-393` deliberately blesses a cross-host endpoint). I filed this at IMPORTANT in round 2; **the lead re-rated it MINOR and deferred it.** Reasoning to carry forward: under an HTTPS gateway, TLS authenticates the discovery document, so there is no MITM rewrite; under plain HTTP the attacker already reads the refresh token in cleartext on every refresh; and a hostile gateway already holds the tokens it issued. Real hardening gap, but it denies an attacker nothing they do not already have. Re-raise only if the transport floor itself is widened.

**Lower-confidence findings from round 2, recorded so they are not rediscovered from scratch** (none accepted for fix): gateway-chosen `user_code`/URL printed to the terminal with no control-char stripping (`login.rs:90-95`); `error`/`error_description` interpolated into messages without `truncate_for_error`, which every raw-body site *does* apply (`login.rs:217`, `login.rs:390`, `auth.rs:228`); `normalize_gateway_url` validates the parsed URL but returns the **raw** string (`login.rs:166`), and `browser_open_refusal` likewise parses `raw` but opens `raw`; the cwd-relative session fallback when `HOME` is unset can let a repo-shipped `.shunt/gateway/session.json` steer `ANTHROPIC_BASE_URL` (`store.rs:66-70` -> `launch.rs:77`, no re-validation on the read path); `logout` is local-only — no `/oauth/revoke` exists server-side, so a copied `session.json` keeps refreshing (docs say "discard the stored session" and do not overclaim); Windows `shell_quote` does not neutralize `cmd.exe` `%VAR%` expansion inside double quotes (`launch.rs:94-97`).

**Why:** the gateway URL is operator-typed, so most of this surface is a trust-boundary call rather than a bug — which is exactly why the accepted residuals are the ones that fail **without** an attacker (a hung host, a units bug, a malformed token). **How to apply:** when reviewing a follow-up PR here, check residuals 1-4 first and re-verify the closed list rather than re-deriving it; if a change widens what the discovery document can steer, or adds a timeout/clamp, re-review the deferred item alongside it.
