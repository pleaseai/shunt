shunt の[ステージルーター](/ja/guides/stage-router/)は独自のスコアリングを発明して
いません。[NVIDIA-NeMo/Switchyard][sy] のルーティングライブラリ
[`switchyard-libsy`][libsy] に依存しています — 「各 LLM 呼び出しを、それでも仕事を
こなせるもっとも安価なモデルへルーティングする」を掲げるプロジェクトです。

このページは統合の記録です。shunt が Switchyard のどの部分を使い、どの部分を意図的に
使わないのか、公開されている数値が実際に何を測ったものなのか、そしてアルゴリズムが
1 ターンをどう判定するのか。機能を有効にする方法だけが必要なら、
[ステージルーターガイド](/ja/guides/stage-router/)のほうが短く読めます。

[libsy]: https://crates.io/crates/switchyard-libsy
[sy]: https://github.com/NVIDIA-NeMo/Switchyard

## shunt が取り込んだもの

Switchyard はゲートウェイ一式を提供します。プロキシサーバー、プロバイダー中立の
プロトコル、リクエスト／レスポンス変換、LLM ジャッジ分類器、エスカレーション、
サブエージェントルーティング。shunt はすでにゲートウェイなので、スコアラー 1 つだけを
取り込み、残りは置いてきます。

| Switchyard コンポーネント | shunt では |
| :-- | :-- |
| `switchyard-libsy` ステージスコアラー | **使用** — `0.2` 系列に固定 |
| `switchyard-protocol` | libsy の依存として入るのみ。shunt は `Request` を組み立てない |
| `switchyard-translation` | **不使用** — shunt の `src/model/responses_request.rs` と真正面から重複 |
| `switchyard-server` | **不使用** — shunt 自身がサーバー |
| LLM 分類器／ジャッジ | **不使用** — [後述](#ホットパスに-llm-ジャッジを置かない)を参照 |
| エスカレーションルーティング（ターン途中） | **不使用** — shunt の post-2xx 無再生ルールと衝突 |
| ハンドオフノート、アドバイザーゲート、サブエージェントルーティング | **不使用** |

結合点は関数呼び出し 1 つだけです。shunt はパース済みの Anthropic Messages ボディから
libsy の `ToolSignals` 構造体を直接埋め、`pick_tier` を呼びます。その構造体の全
フィールドが `pub` なので、あいだに変換層は入りません。

バージョンは `0.2` に固定し、自動アップグレードから除外しています。`0.2.0` が唯一の
公開リリースで、アップストリームの `main` はすでに乖離しています — 向こうの
`ToolSignals` にはフィールドが 4 つ多くあります。API を確認するときは GitHub では
なくレジストリのソースを読んでください。

## ベンチマーク結果

以下は**アップストリーム Switchyard の**数値であり、shunt のものではありません。
shunt は Terminal-Bench を実行しておらず、次の節はその結果がどこまで引き継がれるかに
ついてです。

Terminal-Bench 2.1、Opus 4.8 ベースライン比:

| 構成 | 正解率 | 総コスト | ベースライン比 |
| :-- | --: | --: | :-- |
| Opus 4.8 ベースライン | 76.0% | $98.06 | — |
| エスカレーションルーティング | 75.7% | $85.00 | 正解率の 99.6%、13.3% 安い |
| **ステージルーティング** | **72.7%** | **$68.19** | **正解率の 95.7%、30.5% 安い** |
| ケイパビリティルーティング | 71.2% | $79.32 | 正解率の 93.7%、19.1% 安い |
| Kimi K2.6 単体 | 55.8% | $76.28 | |
| GLM 5.2 単体 | 52.4% | $16.47 | |
| DeepSeek V4 Pro 単体 | 48.7% | $96.92 | |
| Ultra 3 単体 | 39.0% | $29.66 | |

shunt が実装している行であるステージルーティングは、3 つのルーティング構成のなかで
もっとも安く、ベースラインの解決率の 95.7% を保っています。下 4 行がこの数値を
面白くする対照群です。ルーターより高くついたものも含め、**あらゆる**固定モデル単体が
56% を下回っています。

`0.5` というデフォルトを生んだ信頼度しきい値のキャリブレーションは、Terminal-Bench
ではなく SWE-Bench Pro Python-75 から導かれた別作業です。

### shunt に引き継がれるもの、引き継がれないもの

スコアラーは同じコードです。その周りはすべて shunt のものなので、上の表は shunt 自身の
結果ではなく、*このアプローチが*割に合うという証拠として読んでください。

| | アップストリームのベンチマーク | shunt |
| :-- | :-- | :-- |
| スコアリングの中核 | `switchyard-libsy` | 同じクレート、同じ定数 |
| シグナル抽出 | アップストリームのプロバイダー中立な抽出 | shunt 独自、Anthropic Messages ブロックから |
| `tests_passed` / `compacted` | スコアラーが利用可能 | 常に `false` — 一度も埋められない |
| 曖昧なターンのジャッジ | 任意で利用可能 | なし。ピッカーのデフォルトへ fall-open |
| ターンをまたぐティアの安定性 | ターンごとに独立採点 | 非対称ヒステリシス付きのセッションピン留め |
| ワークロード | Terminal-Bench 2.1 のタスク | Claude Code のセッション |

このうち 2 つは逆向きに働きます。shunt は `tests_passed` と `compacted` を埋めない
ため、libsy のハードな降格ショートカットとコンパクションのオーバーライドが落ちます —
ベンチマークより厳密にシグナルが少ない状態です。その一方で shunt のヒステリシスは、
ベンチマークハーネスが決して払わないコスト、すなわち Claude Code セッションで
ティアを毎ターン切り替える高さがあるからこそ存在します（[後述](#shunt-が加えるもの)）。

## ルーティングアルゴリズム

### 1. シグナル

shunt はリクエストの `messages` 配列を 2 回走査します。1 回目はアシスタント
メッセージを `recent_turn_window` が届く範囲まで後ろから走査し、*最近*として数える
`tool_use` の id を集めます。2 回目は両方のロールを前から 1 度だけ走査し、
`tool_use.id → tool_use.name` を作りつつ、すべての `tool_result` をそれが答えた
`tool_use_id` に紐づけて記録します。名前は走査中ではなく走査後に解決するので、自分の
呼び出しより前に現れた結果もそのまま突き合わせられます。`tool_result` ブロックは
ツール名を持たないので、この突き合わせが抽出器全体を支える唯一の足場です。

突き合わせに使う id を除けば、読むフィールドは `tool_use.name` と
`tool_result.is_error` の 2 つだけ。システムプロンプトも、ユーザーのテキストも、
ツール引数も読みません。

Claude Code は失敗を等級なしの真偽値でしか報告しないため、shunt 自身が libsy の
`0.0 / 0.3 / 0.7 / 1.0` という深刻度スケールへ対応づけます。

| 条件 | `severity` |
| :-- | :-- |
| ウィンドウ内に失敗結果なし | `0.0` |
| ウィンドウ内に失敗結果あり | `0.7`（hard） |
| ウィンドウ内の `Task` の失敗 — 委譲されたサブエージェント実行まるごとの崩壊 | `1.0`（critical） |
| 直近 2 件の完了結果がどちらも失敗し、どちらもウィンドウ内 — 回復していない | `1.0`（critical） |

ツール名は[語彙](/ja/guides/stage-router/#ツールの語彙)に従って `Observe`、`Mutate`、
`Plan`、未分類に振り分けられます。`Bash` は意図的に未分類です — `git status`、
`rm -rf`、`cargo test` を分けられるのは `input.command` を読むことだけであり、それこそ
この設計が避けている脆い推論です。

完了したツール呼び出しが 1 つもなければ抽出は何も返さず、ターンはピッカーの
デフォルトになります。空の会話が「efficient」と採点されることはありません。

### 2. ディメンション

シグナルは 2 つの軸に射影されます — 何かが*おかしい*か、そしてエージェントが
*生産している*か。

| ディメンション | 意味 | 押す方向 |
| :-- | :-- | :-- |
| `severity` | ウィンドウ内の最大エラー深刻度、`[0, 1]` | Capable |
| `spinning` | 読み・計画・書き・編集のいずれもない深いターン — 純粋な空転 | Capable |
| `exploring` | 読むか計画するが、書きも編集もしない深いターン | Capable |
| `production_intensity` | 直近のツール操作に占める書き＋編集の割合 | Efficient |

`spinning` と `exploring` はどちらも `turn_depth >= 8` を要求します。書き込みのない
序盤のターンは停滞ではなく通常の探索だからです。両者は同じ「生産していない」状態を
調査活動の有無で分割するので、発火するのは高々 1 つであり、生産軸が二重計上される
ことはありません。

### 3. スコア

最大に達したディメンション 1 つが `0.10` のシグナル単位 1 つを寄与し、`severity` は
hard 上限の `0.7` で正規化されて同じ重みに揃えられます。

```
raw   = 0.10 × (severity / 0.7 + spinning + exploring − production_intensity)
score = tanh(5.0 × raw)          // 符号: + capable, − efficient
confidence = |score|
```

ゲイン `5.0` がレンジを使える幅に広げます。これがなければ信頼度は `±0.20` 付近で
頭打ちになり、意味のあるしきい値には決して届きません。

設計は**相互補強的**です。単一の軸だけで判定を決め切ることはできません。

| 一致するシグナル | `raw` | `confidence` | `0.5` のデフォルトを超えるか |
| :-- | --: | --: | :-- |
| 1 つが飽和 | `0.10` | `tanh(0.5) ≈ 0.46` | いいえ |
| 2 つが相互補強 | `0.20` | `tanh(1.0) ≈ 0.76` | はい |

`0.5` というデフォルトはここから来ています。誤ったシグナル 1 つだけではターンを
動かすのに足りず、一致するシグナル 2 つなら足ります。

### 4. 判定

`pick_tier` は 4 つのルールを順に走らせ、最初に発火したものが勝ちます。

1. **ハード昇格** → capable。critical な深刻度、またはコンパクションされたコンテキスト。
   スコアラーを飛ばし、`confidence: 1.0` を報告します。
2. **ハード降格** → efficient。テストが通り、コードが直近で書かれ、何もエラーして
   いない。スコアラーを飛ばし、**信頼度をまったく報告しません**。
3. **スコアラー。** `confidence >= confidence_threshold` なら符号に従います。
4. **Fall-open。** しきい値未満なら libsy が `ConsultClassifier` を返します。shunt は
   分類器を走らせないので、ターンはピッカーのデフォルトティアに着地します。

昇格が降格より先に判定されるので、たまたまテストも通ったターンでも critical エラーが
勝ちます。

今日の shunt ではルール 2 は発火しえません。抽出器が `tests_passed` を無条件に
`false` にしているからで、これを判定するには Claude Code の `Bash` 結果*テキスト*の
パターンマッチが必要になり、外したときにちょうど痛い方向へ高くつきます。ルール 1 の
コンパクション側も同じ理由で眠っています — 固定されたコンパクションマーカーがまだ
ありません。critical な深刻度は、上の深刻度表の 2 経路を通じて今もルール 1 を
発火させます。

### 5. ヒステリシス

ここまではターンを単独で判定します。そのうえで shunt は、その判定がセッションの
ピン留めされたティアを動かすことを許す前に、独自のゲートをかけます。

| 方向 | 要件 |
| :-- | :-- |
| Efficient → Capable | スコアラーが実際に下した判定が `confidence_threshold`（0.5）を超えること |
| Capable → Efficient | スコアラーが実際に下した判定、**かつ** `min_dwell_turns` の経過、**かつ** `deescalate_threshold`（0.75） |

Fall-open、曖昧なターン、ツール活動のないターンは証拠ではなくピッカーのデフォルトで
あり、どちらの方向にもピンを動かせません。

`tests_passed` のショートカットは*信頼度*ゲートからは免除されますが、dwell からは
されません — 信頼度をまったく報告しないため、素朴な `confidence >= threshold` を
かけると、安く下がるためのもっとも強い根拠が唯一発火しえない根拠になってしまいます。
この免除は上記の理由で今日は不活性であり、あとでシグナルを埋める作業が抽出器だけの
変更で済むように残されています。

## shunt が加えるもの

Switchyard はプロバイダー中立なので、ティア切り替えの値段を付ける必要がありません。
shunt は Claude Code ゲートウェイなのでその必要があり、ここに並ぶものの多くはその
違いから生まれています。

### Claude Code の実際のツール語彙

スコアラーが知りたいのは、ある呼び出しが観測したのか、変更したのか、計画したのかです。
プロバイダー中立なルーターはそれを推論するしかありませんが、shunt は名前を知っており、
14 個を直接マッチします。観測は `Read`、`Glob`、`Grep`、`NotebookRead`、`WebFetch`、
`WebSearch`、`BashOutput`、変更は `Edit`、`NotebookEdit`、`Write`、計画は `TodoWrite`、
`Task`、`EnterPlanMode`、`ExitPlanMode` です。うち 1 つはカテゴリ以上の扱いを受けます —
*失敗した* `Task` はコマンド 1 つではなく委譲されたサブエージェント実行まるごとの崩壊なので、
hard ではなく critical として採点されます。

### 切り替えはタダではない、だから非対称ヒステリシス

長い Claude Code セッションでは、ティア切り替えは具体的に 3 つを支払います。

- **プロンプトキャッシュはモデルごとにキーが張られます** — 切り替えると温まった
  プレフィックスを失い、新しいティアでキャッシュ書き込みを全額払います。
- **Codex の継続**はモデルをシグネチャにハッシュするので、切り替えは完全な再送を
  強制し、shunt がいま稼いだアップロード削減を返してしまいます。
- **プロバイダーをまたぐ切り替え**は、セッションのプール済み接続とスティッキーな
  アカウントスロットまで捨てます。

毎ターン独立に採点すると、長いセッションはルーティングしないときより*高く*つき
えます。2 つの方向が不平等である理由であり、ヒステリシスが shunt の統合における
枝葉ではなく中核である理由です。

### セッション id を漏らさないセッションピン留め

判定は `(広告されたモデル id, セッション id)` 単位でピン留めされ、キーは SHA-256 の
プレフィックスです — セッション id はハッシュされ、保存されません。ストアは 4096
セッションで上限に達し、挿入パス上で追い出しを行うためバックグラウンドタスクはなく、
何も永続化しません。

ピンは自分が作られたルーターテーブルのフィンガープリントも覚えているので、ホット
リロードをまたいでルーター 1 つを編集しても、落ちるのはそのルーターのピンだけです。
そのフィンガープリントは設定構造体をドット参照ではなく分解束縛で読むため、あとから
キーが増えたときは、古いピンが黙って生き延びる代わりにコンパイルが壊れます。

### ホットパスに LLM ジャッジを置かない

シグナルが決め手を欠くとき、libsy は
`PickOutcome::ConsultClassifier { default_tier }` を返します。shunt はそれを答えとして
扱い、`default_tier` を採ります。ジャッジを断るのは API と戦うことではなく、API が
文書化した fall-open の経路*そのもの*です。

得られるのは、2 回目のモデル呼び出しがないこと、2 つ目の資格情報がないこと、そして
ルーターがもっとも自信のないターンでレイテンシが増えないことです。支払うのは、
そうしたターンでジャッジが取り戻したはずの正解率であり、これはアップストリームの
分類器併用構成が測ったものの実質的な一部です。

### ルーティング先は普通のモデル id

ルーターの出力は公開モデル id なので、shunt の通常のルーティング階段に再び入り、
フェイルオーバーチェーン、アカウントプール、アダプター選択、`effort`、`service_tier`
をそのまま受け継ぎ、追加のコードなしに `/v1/models` のディスカバリーに現れます。
ターゲットがまたルーターであれば起動エラーなので、解決は深さカウンターではなく
**構造的に** 1 ホップです。

### クライアントは今も自分が要求した id を見る

ティアは `upstream_model` に乗って上流へ行くだけです。レスポンスは要求された id を
報告するので、Claude Code の `/model` 表示と `--resume` のモデル復元はそのまま
動きます。

### 頼まない限り不活性

`[models.stage_router]` テーブルがなければ、ルーターの分岐は既存のデプロイが持って
いない設定フィールドに対する `Option` チェック 1 つです。ルーティング経路について
変わるものはありません。

## 統合のコスト

依存を採用した際に、見積もりではなく実測した値です。

| | |
| :-- | :-- |
| リリースバイナリ | **+115,376 バイト（+0.31%）** |
| `Cargo.lock` のパッケージ | **+33**（412 → 445） |
| うち未使用 | 約 26。shunt が呼ばない分類器パスのための `jsonschema` ツリー |
| 実際にリンクされるか | `jsonschema` ツリーはリンクされ**ません** — ビルド済みバイナリに `jsonschema` 文字列 0 件、`num-bigint` シンボル 0 件 |
| 移植という代替案 | 137 行 |

決め手はバイナリの結果でした。リンカが分類器ツリーをまるごと落とすので、クレートに
依存するコストは 0.3% 程度です。137 行の移植は、固定したリリースが陳腐化した場合の
出口として記録に残っています。
