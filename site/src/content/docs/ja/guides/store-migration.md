---
title: ストアへの移行
description: プールのクォータ、ゲートウェイの refresh token、支出上限を JSON の state_path スナップショットから SQLite または PostgreSQL のストアへ移し、一度きりのインポートがすべてのスナップショットを取り込んだことを確認します。
---

[`[store]`](/ja/reference/configuration/#storeオプション) がない場合、shunt はプールのクォータ、ゲートウェイの refresh token、支出上限を、サブシステムごとに 1 つずつ、計 3 つの JSON スナップショット（`state_path`）に保存します。`[store]` を追加すると、これらはトランザクション対応のデータベース 1 つに置き換わります。専用の移行コマンドはありません。`[store]` を設定して最初に実行する `shunt run` が各スナップショットを一度だけインポートし、以降そのサブシステムはストアから提供されます。

インポートはサブシステムごとに一度だけ実行され、繰り返すことはできません。最初の起動の前にパスを正しく設定してください。そのとき見つからなかったスナップショットは、後からインポートされることはありません。

## インポートされるもの

| サブシステム | スナップショット | インポートされる条件 |
| :-- | :-- | :-- |
| プールのクォータ | `[server.pool] state_path`（デフォルトなし） | `[store]` が設定されている |
| ゲートウェイの refresh token | `[server.gateway] state_path`、デフォルトは `~/.shunt/gateway-sessions.json` | `[server.gateway]` が設定されている |
| 支出上限と監査記録 | `[server.spend] state_path`、デフォルトは `~/.shunt/gateway-spend.json` | `[server.spend]` が設定されている |

設定されていないサブシステムはスキップされ、記録も残りません。そのため `[server.gateway]` や `[server.spend]` を後から有効にした場合、そのスナップショットは有効化後の最初の起動でインポートされます。

一部の状態はストアの外に残ります。プロバイダーの資格情報ファイル、管理ブラウザーセッション、OIDC の状態、クールダウン、そして `<stem>.counters.json` にある支出メーターのカウンターです。

## 1. スナップショットを探してバックアップする

設定済みの各サブシステムの `state_path` を、上記のデフォルトも含めて一覧にし、shunt プロセスが参照する場所にファイルがあることを確認します。デフォルトは shunt を実行するユーザーのホームディレクトリを基準に解決されるため、systemd やコンテナ内では自分のホームディレクトリと異なる場合があります。shunt はホームディレクトリを `HOME` から読み、なければ `USERPROFILE` を使います。どちらも設定されていない場合、ゲートウェイと支出のサブシステムにはデフォルトのスナップショットがないため、最初の起動で `NoSnapshot` が記録され、以後もインポートされません。その場合は各 `state_path` を明示的に設定してください。

ファイルは安全な場所にコピーしておきます。shunt はインポート中にしか読み込まず、ストアが接続されている間は書き込みませんが、移行前の状態を後から確認する手段はこのコピーだけです。

## 2. `[store]` を追加する

`state_path` のキーはすべてそのまま残します。`[store]` を設定すると、これらのキーがインポート元を shunt に伝えます。

```toml
[store]
backend = "sqlite"
url = "/var/lib/shunt/shunt.db"
```

PostgreSQL の場合は、`backend = "postgres"` と `postgres://` URL を設定します。ループバック以外のホストには `sslmode=verify-full` が必要です。すべてのキーは [`[store]` リファレンス](/ja/reference/configuration/#storeオプション)にあります。

## 3. `shunt check` を実行する

```bash
shunt check
```

```text
config ok
store ok: sqlite sqlite:/var/lib/shunt/shunt.db, file does not exist yet; it is created with mode 0600 at boot
```

`check` はストアを読み取り専用で開き、マイグレーション、インポート、SQLite ファイルの作成を行わないため、実行中のインスタンスを停止する前に実行できます。設定エラーやストアに接続できない問題は、起動時ではなくここで失敗します。

## 4. 実行中のインスタンスを停止する

現在の shunt を正常終了させます。ストアがない場合、refresh token と支出上限は変更のたびにスナップショットへ書き込まれるため、すでに最新です。プールクォータは異なります。ストアを使わない shunt はプールクォータを 15 秒ごとに保存し、終了時には改めて保存しないため、スナップショットには直近最大 15 秒分のクォータ変更が含まれないことがあります。クォータはアップストリームの応答から再計算されるので、影響を受けるアカウントが短時間コールドスタートする程度のコストです。それも避けたい場合は、トラフィックを止めて 15 秒待ってから shunt を停止してください。ストアを使わないプロセスがインポート後にスナップショットへ書き込んだ内容はストアに反映されません。古いインスタンスが終了するまで、新しいインスタンスを起動しないでください。

## 5. ストアを使って shunt を起動する

```bash
shunt run
```

shunt はリクエストを処理する前に、データベースを作成またはマイグレーションし、サブシステムごとに 1 つのトランザクションで各スナップショットをインポートして、ストアから状態を復元します。起動ログの `store opened; state is served from it` の行に、各サブシステムの結果が出力されます。

| 結果 | 意味 |
| :-- | :-- |
| `Imported { rows: N }` | スナップショットをストアにコピーした |
| `NoSnapshot` | パスが未設定か、ファイルがなかった。記録が書き込まれたため、**このサブシステムは二度とインポートされない** |
| `AlreadyImported` | 以前の起動でこのサブシステムは処理済み |
| `Off` | サブシステムが設定されていないため、ストアを使わない |

インポートに失敗すると、`importing the <subsystem> state snapshot <path> into the store failed` の後にコロンと原因が続くエラーで起動が止まります。そのサブシステムは何もインポートされていません。ただし原因がコミットの失敗の場合はインポートが反映済みのことがあり、次の起動では修正したスナップショットを読み直さず、そのサブシステムを `AlreadyImported` と報告します。それ以前にインポートされたサブシステムの行は残ります。原因に応じて対処してください。スナップショットの形式が不正、またはサポートされないバージョンなら示されたファイルを修正または削除し、ファイルを読み取れないなら権限やパスを直し、ストアのトランザクションが失敗したならストア自体を確認します。その後、もう一度起動してください。その他のストア起動エラーは [トラブルシューティング](/ja/reference/troubleshooting/) を参照してください。

## 6. インポートを確認する

- インポートした各スナップショットの隣には、通常、バックエンド、時刻、スナップショットの SHA-256 を記録した `<state_path>.imported` ファイルができます。shunt はインポートをコミットした後にこのファイルを書き込み、書き込めない場合（たとえばスナップショットのディレクトリが読み取り専用の場合）は `imported the snapshot but could not write its .imported sidecar` という警告をログに出して処理を続けます。ファイルがなくてもインポートが失敗したとは限りません。判断の基準は起動ログの結果と `import_record` です。
- ストアには、ストアを使うサブシステムごとに `import_record` の行が 1 つあります。SQLite の場合:

  ```bash
  sqlite3 /var/lib/shunt/shunt.db \
    'SELECT subsystem, source_path, row_count FROM import_record'
  ```

  `source_path` が `NULL` の場合、そのサブシステムのスナップショットは見つからなかったことを意味します。
- ゲートウェイのクライアントは再サインインせずに動作し続け、`[server.admin]` の認証情報を `x-shunt-admin-token`（デフォルトの管理ヘッダー）または `x-api-key` に付けて送った `GET /v1/organizations/spend_limits`（[エンドポイント](/ja/reference/endpoints/)）は以前と同じ支出上限を返します。

## スナップショットを取り逃した場合

想定外の `NoSnapshot` は、たいてい最初の起動でパスが間違っていたことを示します。ホームディレクトリが違ったか、ファイルがまだなかったかのいずれかです。後からファイルを置いても何も変わりません。インポートの要否は、テーブルが空かどうかではなく `import_record` の行で決まるためです。

SQLite で、最初の起動以降にゲートウェイがトークンを発行、更新、失効させておらず、支出上限も変更されていない場合は、shunt を停止し、データベースファイルを `-wal` と `-shm` ファイルごと削除してパスを直し、もう一度起動します。スナップショットは変わっていないので、すべてのサブシステムが改めてインポートされます。その間に保存されたプールクォータも失われますが、アップストリームの応答から再計算されます。トークンや上限が変わった後はリセットしないでください。古いスナップショットを再インポートすると、その間に失効させた refresh token が復活し、代わりに発行されたトークンは失われます。

## 元に戻す

インポートは同期ではなくコピーであり、shunt はストアの状態を JSON に書き戻しません。`[store]` を削除すると、各サブシステムはインポート時点のスナップショットから開始するため、失効させたセッションが復活したり、その後に行った支出上限の変更が取り消されたりすることがあります。スナップショットがインポート後に変更されていない間は、ストアなしで起動するとその旨の警告がログに出力されます。詳細は [ストアなしに戻す](https://github.com/pleaseai/shunt/blob/main/docs/store.md#going-back-to-no-store)（英語）を参照してください。
