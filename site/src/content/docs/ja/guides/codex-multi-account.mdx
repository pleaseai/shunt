description: ChatGPT/Codex サブスクリプションの OAuth アカウントをプールし、セッションスティッキーでクォータを考慮したプロアクティブな選択とリアクティブなフェイルオーバーで運用する。
---

shunt は、`chatgpt_oauth` プロバイダー — 組み込みの `codex` プロバイダー、またはその認証モードを使う任意の `responses` プロバイダー — の背後で、複数の ChatGPT サブスクリプション OAuth 認証情報をプールできます。Claude Code が `x-claude-code-session-id` を送る場合、リクエストはセッションスティッキーになります。ヘッダーがないリクエストはプロバイダーごとのラウンドロビンを使います。[Anthropic アカウントプール](/ja/guides/anthropic-multi-account/)と同様に、選択は**クォータを考慮**します。shunt はバックエンドの `x-codex-*` 5 時間 / 7 日の使用量ウィンドウを記録し、クォータに近づいたスティッキーアカウントをプロアクティブにローテーションで外します。一方で、クールダウンに基づくリアクティブなフェイルオーバーが安全網として残ります。

クライアント向けの [`GET /usage`](/ja/reference/endpoints/) 集約では、無効化されていないアカウントが報告していないウィンドウだけが `null` になります。Codex の `x-codex-*` レスポンスヘッダーは 5 時間と共有週次ウィンドウを埋めます。Codex には Fable スコープ（`7d_oi`）のシグナルがありませんが、混在プロバイダーのプールでは別のプロバイダーが集約 Fable 値を提供できます。このブランチには帯域外 Codex ポーラーがありません。ChatGPT バックエンドには非公開・未文書化の usage API がありますが、#430 用に確保されており、このブランチからは呼び出しません。



<Aside type="caution" title="サブスクリプション規約">

サブスクリプションの認証情報は、アカウント規約が許す範囲でのみ使用してください。shunt は非公式クライアントであり、OpenAI のアカウント/サブスクリプションポリシーを変えるものではありません。

</Aside>



## プールを設定する

まず Codex CLI でログインします — shunt は ChatGPT のログインを自身で実行することは決してなく、`codex login` がすでに書き込んだ認証情報をインポートするだけです。

```bash
codex login
```

続いて `auth = "chatgpt_oauth"` を設定し、明示的なアカウントエントリーを追加します。

```toml
[providers.codex]
kind = "responses"
base_url = "https://chatgpt.com/backend-api"
auth = "chatgpt_oauth"

# A second Codex CLI login, imported under a distinct name.
[[providers.codex.accounts]]
name = "primary"
credentials = "~/.shunt/accounts/codex/primary.json"

# A raw ChatGPT access token supplied out of band. Used verbatim; not refreshed.
[[providers.codex.accounts]]
name = "backup"
token_env = "CODEX_BACKUP_ACCESS_TOKEN"
```

```bash
export CODEX_BACKUP_ACCESS_TOKEN='<a valid ChatGPT access token>'
shunt check
shunt run
```

Codex CLI のログインを shunt 自身のストアへインポートすることで、アカウントを保存できます。

```bash
shunt login codex --name primary
```

その後は名前だけのエントリーを使います。

```toml
[[providers.codex.accounts]]
name = "primary"

[[providers.codex.accounts]]
name = "backup"
```

ストアファイルは `~/.shunt/accounts/codex/<name>.json` に置かれます。`SHUNT_CODEX_ACCOUNTS_DIR` でディレクトリを上書きできます。設定された `accounts` リストが空の場合、shunt はストアをスキャンし、有効な JSON アカウントファイルすべてをファイル名順に使います。ストアファイルはプライベートで（Unix では `0600`、ディレクトリは `0700`）、Codex CLI 自身の `auth.json` の形をそのまま保持します — Claude のストアとは異なり、ラッパーオブジェクトはありません。

`shunt login codex` に `--long-lived` フラグはありません — Codex に setup-token の概念はないため、ストア管理のアカウントはすべて、既存の `codex login` からインポートされたリフレッシュ可能な OAuth ログインです。

インポートが受け付けるのは **ChatGPT** ログインだけです。現行の `codex login` は `$CODEX_AUTH_FILE`（または `~/.codex/auth.json`）に `"auth_mode": "chatgpt"` を書き込みます。shunt はこのフィールドを大文字小文字を区別せずに比較するため、古い Codex が残したファイル（`"ChatGPT"`）もそのままインポートできます。API キーのログイン（`"auth_mode": "apikey"`）は `is not a ChatGPT login (auth_mode is not "chatgpt")` として拒否されます — `codex login` をやり直して ChatGPT アカウントを選んでください。

## アカウントのフィールド

| フィールド | 必須 | 意味 |
| :-- | :-- | :-- |
| `name` | はい | 小文字・数字・ハイフンのみからなる一意のラベル。他のソースフィールドがない場合、名前が一致する shunt ストアファイルを解決します。 |
| `credentials` | 使用可能なソースのいずれか 1 つ | Codex CLI の `auth.json` 形式のファイル。shunt は期限が近づくとリフレッシュし、リフレッシュ済みトークンをアトミックに書き戻します（`~/.codex/auth.json` そのものと同じ挙動です）。 |
| `token_env` | 使用可能なソースのいずれか 1 つ | 生の ChatGPT アクセストークンを含む環境変数。値はそのまま使われ、401 の後にリフレッシュできません。 |
| `uuid` | いいえ | エイリアスを統合するために使われる、安定した上流のアイデンティティ。名前のみのエントリ（ストアスキャンで解決）は選択が行われる前に自動的に埋められるため、ストアスキャンで検出されたエイリアスは設定変更なしで統合されます。`credentials` または `token_env` で設定されたエントリのアカウント id は選択の後にのみ解決され、`uuid` に書き込まれることはありません。そのため、そうしたエントリのアイデンティティは、設定されていれば `uuid`、なければ `name` です。そのアイデンティティが他のエイリアスの明示的な `uuid` または名前フォールバックのアイデンティティと一致するたびに統合されるため、明確で意図的な統合のためには両方のエントリに一致する空白だけでない `uuid` を設定してください（shunt は `uuid` と `name` の偶発的な衝突についても警告します）。この値が Codex のリクエストボディへ書き込まれることはありません。 |
| `priority` | いいえ | 利用可能なアカウント間での選択優先度。値が小さいほど優先され、デフォルトは `100` です。Codex 経路でも有効です。 |
| `disabled` | いいえ | `true` にすると、設定には残したまま、アカウントを選択対象から完全に除外します。Codex 経路でも有効です。 |

1 つのアカウントに `credentials` と `token_env` の両方を設定しないでください。

## アカウント id の解決

Codex には設定可能な明示的な `uuid` フィールドがありません。代わりに shunt は、各アカウントについて次を行います。

1. 保存された `tokens.account_id` を優先します。
2. なければ `access_token` の JWT をデコードし、`chatgpt_account_id` クレームを読み取ります。
3. リフレッシュ後は、新しいアクセストークンの JWT クレーム**のみ**から id を再計算します（リフレッシュのレスポンスに独立したアカウント id フィールドはありません）。

どちらのソースからも id が得られない場合、そのアカウントは解決に失敗し、後述の認証情報解決の失敗として扱われます。解決された id を選択の前にメモリ上のアカウントの `uuid` フィールドへ書き込むのは、ストアスキャン（`accounts` リストが空の場合）だけです — `credentials` / `token_env` で設定されたアカウントの id はリクエストごとに解決され、`uuid` へフィードバックされることはありません。ストアの*スキャン*自体はストアディレクトリの mtime でキャッシュされるため、定常状態のディスカバリーはディレクトリの `stat` 1 回だけで済み、認証情報ファイルの読み取りは発生しません。選択されたアカウントの実際の認証情報の解決では、期限の確認/リフレッシュに必要な範囲で、引き続きリクエストごとにその認証情報ファイルを読み取ります。



<Aside type="note" title="同一の実アカウントに対する重複した名前">

2 つのストアファイルまたは設定エントリが同じ `account_id` を持つ場合、shunt はそれらを **1 つのアカウント**として数えます。クールダウン、ヘルス、リフレッシュロックを共有し、フェイルオーバーは同じ ChatGPT アカウントを再試行せず、重複したエイリアスをスキップします。スティッキーハッシュとラウンドロビンは別個のアイデンティティ単位で動作します。代表となるのは `priority` が最も低い有効なエイリアス、次いで最初のエントリで、その代表のトークンだけが試行され、shunt は重複アイデンティティの警告をログに出力します（設定エントリはリロードを含め設定の読み込みに成功するたびに一度、ストア検出による衝突は重複集合ごとに一度で、いずれもリクエストごとではありません）。そのため、代表が無効であっても、有効な非代表エイリアスによって救済されることはありません。

admin web サーフェスからストア管理アカウントを削除すると、そのアイデンティティを共有する他のストアエイリアスが残っていない場合に限り、共有プロセス内ヘルスがクリアされます。スキャンに失敗した場合は、推測せずヘルスを保持します。これは admin ストア削除の挙動であり、TOML 設定からエイリアスを削除したり、その認証情報ファイルを直接削除したりする操作はこのクリーンアップを経由しません。

</Aside>



## 選択とクールダウン

- `x-claude-code-session-id` がある場合: 安定したハッシュがスティッキーアカウントを選びます。Anthropic プールと同じ仕組みです。
- ヘッダーがない場合: プロバイダーごとに独自のラウンドロビンカウンターを持ちます。
- 成功レスポンスは `x-codex-primary-*` と `x-codex-secondary-*` ヘッダーから使用量を記録します。shunt は各グループを `window-minutes` でマッピングします。約 300 分は 5h、約 10080 分は 7d に現れ、それ以外のウィンドウは無視されます。グループの `x-codex-*-reset-at` ヘッダーが空でも、shunt はその位置に対応するウィンドウグループと使用量を記録します。リセットがない場合、使用量は自身の観測時刻からウィンドウ長が経過した時点で失効します。Codex に `7d_oi` 相当はありません。
- 記録された使用量は、[Anthropic プール](/ja/guides/anthropic-multi-account/)とまったく同じように選択へ供給されます。しきい値（組み込みの `0.98`、または [`[server.pool]`](/ja/reference/configuration/#serverpoolオプション) / アカウント単位のソフトしきい値）に達したスティッキーアカウントは、最も余裕のあるアカウントへプロアクティブに道を譲り、`burn_rate_avoidance` と priority / 余裕（headroom）による順序付けが適用されます。`x-codex-rate-limit-reached-type` の値は表示用にのみ記録されます。
- `[server.pool] ramp_initial_concurrency` を設定すると、スロースタートの受け入れゲートが、フェイルオーバー直後に選択されたばかりのアカウントへ殺到が起きるのを防ぎます。[`[server.pool]`](/ja/reference/configuration/#serverpoolオプション) を参照してください。
- `[server.pool]` を設定すると、陳腐化した近接クォータアカウントが `reprobe_seconds`（デフォルト 900 秒、`0` で無効）ごとに一度、選択順の先頭へ日和見的に昇格され予約されます。admission または認証情報の解決に失敗すると予約を取り消し、最初の HTTP 送信時に再プローブ時刻と `shunt.pool.reprobes` をコミットします。[`[server.pool]`](/ja/reference/configuration/#serverpoolオプション) を参照してください。WebSocket 転送を有効にしたプロバイダーの outbound Responses プールは予約を作らず、この再プローブを抑止します。オプションの inbound Codex HTTP エンドポイントは引き続きプローブするため、カウンターは inbound プローブだけを数えます。Codex usage ポーラーがない場合、除外された outbound マークは観測時刻に基づくウィンドウ寿命の上限で期限切れになるまで残ります。鮮度は、5h、共有 7d、Fable 7d_oi の各ウィンドウで使用量観測と status 観測の新しい方を取り、4 つ目に独立した aggregate status 観測を使って判定します。使用量だけのポーリングは使用量の鮮度だけを更新し、各ウィンドウの status 鮮度は更新しません。
- 成功レスポンスは、そのアカウントのクールダウンを解除します。

| トリガー | クールダウン |
| :-- | :-- |
| 認証情報の解決失敗（アカウント id / トークンが解決不能） | 5 分 |
| トランスポート/接続の失敗 | 30 秒 |
| 上流の 5xx レスポンス | 30 秒 |
| 上流の 429 レスポンス | 数値の `retry-after`（1〜3600 秒にクランプ、デフォルト 60 秒） |
| `token_env` アカウントでの 401 | 5 分 |
| `credentials` / ストアアカウントでの 401 で、リフレッシュに失敗、またはリトライしてもまだ 401 | 5 分 |

## フェイルオーバーのルール

| レスポンス | 挙動 |
| :-- | :-- |
| 2xx | 中継し、健全としてマークします。 |
| 429 | **常に**クールダウンしてローテーションします。オプションの Codex 拒否シグナルは表示用に記録されますが、フェイルオーバーの分類は変えません。したがって、すべての 429 はそのアカウントの枯渇として扱われます。 |
| `credentials` / ストアでの 401 | 強制リフレッシュして同じアカウントを 1 回リトライします。リフレッシュに失敗、またはリトライしてもまだ 401 なら、5 分クールダウンしてローテーションします。 |
| `token_env` での 401 | リフレッシュ不可: 5 分クールダウンしてローテーションします。 |
| 5xx またはトランスポート障害 | 30 秒クールダウンしてローテーションします。 |
| 認証情報の解決失敗 | 5 分クールダウンしてローテーションします。 |
| その他のステータス（例 `400`） | フェイルオーバーせずに中継し、アカウントを健全としてマークします。 |

分類はレスポンスボディがストリーミングされる前に行われるため、ストリーム途中の失敗が再送されることはありません。プールが少なくとも 1 つの上流レスポンスを受け取った後に試行を使い切った場合、shunt はその最後のレスポンスから組み立てた**変換済み**の Anthropic 形式エラーエンベロープを中継します — ステータス（例 `429`）は保たれますが、ボディはそのまま中継されるのではなく作り直されます。これは、最後の上流レスポンスをバイト単位でそのまま中継する Anthropic プールとは逆の挙動です。どの上流レスポンスも得られないまますべてのアカウントが失敗した場合、通常の Anthropic Messages ルート（`/v1/messages`）は、ゲートウェイ自身の `502 api_error` を `all upstreams failed (N attempted)` とともに返します。別個の `[server.codex_endpoint]` インバウンド経路は影響を受けず、`all Codex OAuth accounts failed before receiving an upstream response` を維持します。

## リクエストとレスポンスの変更

選択されたアカウントに対し、shunt は単一アカウント経路と同じ Codex CLI の identity ヘッダーを、そのアカウントの認証情報から埋めて送信します。

```http
authorization: Bearer <selected account's access token>
chatgpt-account-id: <selected account's account id>
originator: codex_cli_rs
OpenAI-Beta: responses=experimental
```

プール経由のレスポンスはアカウントを識別します。

```http
x-shunt-account: backup
```

共有ゲートウェイでは中立的なアカウント名を使ってください — このヘッダーは、レスポンスを受け取るすべての認可済みクライアントへ、設定されたラベルを公開します。プール枯渇後の最後の変換済みエラーの中継では `x-shunt-account` は省略されます。

### WebSocket トランスポート

プロバイダーが `websocket = true` も設定している場合（[ChatGPT / Codex](/ja/guides/codex/) を参照）、プールされたコネクションキャッシュのキーはアカウントごとにプレフィックスされるため、2 つのアカウントがソケットや `previous_response_id` の継続状態を共有することはありません。トークンがまだ 1 つもストリーミングされていない**時点**での WebSocket の失敗は、**同じ**アカウントで HTTP へフォールバックします（プールのローテーションではありません）。フェイルオーバーが起きるのは HTTP 経路での失敗だけです。新規の WebSocket アップグレードは、そのハンドシェイクから得られるレート制限ヘッダーを記録します。再利用/プリウォームされたコネクションは再度ハンドシェイクしないため、ダッシュボードの使用量は新しいコネクションが確立されたときに更新されます。

## セキュリティ上の制約

`chatgpt_oauth` は次の場合にのみ受け入れられます。

- `base_url` が HTTPS を使っている。
- ホストが `chatgpt.com`、またはそのサブドメインである。

`xai_oauth` と同様に、**`chatgpt_oauth` は `kind = "responses"` を必要とします** — これは `openai` や `xai` と共有される Codex バックエンドの kind です。これはベアラー漏洩のガードです。Codex のベアラーを注入するのは Responses アダプターだけなので、`kind = "anthropic"` の不一致なプロバイダーは Anthropic アダプターへルーティングされ、代わりにクライアント自身の認証情報をオリジン外の `chatgpt.com` へ転送してしまいます。これらの起動時チェックは、OAuth ベアラーがオリジン外へ、あるいは平文で送られるのを防ぎます。HTTPS とホストのチェックは**ループバックホストでは緩和**されます（`localhost`、`127.0.0.1`、`[::1]` など）。ループバックの `base_url` は平文 HTTP と任意のホストを使えるため、ローカルのデバッグプロキシやモックがトラフィックを受け取れます。非ループバックのホストには常に HTTPS + `chatgpt.com` が求められます。共有デプロイでは、`chatgpt_oauth` がゲートウェイ所有の認証情報を消費するため、[`[server.auth]`](/ja/guides/shared-gateway/) も設定してください。

## 影響を受けないもの: 単一アカウント経路

`accounts` が設定されていない `chatgpt_oauth` プロバイダー（デフォルトの `codex` プロバイダー）は、これまでどおりに動作します。`~/.codex/auth.json`（または `$CODEX_AUTH_FILE`）を直接読み取ってリフレッシュし、クールダウンも `x-shunt-account` ヘッダーもありません。

## 残りのフォローアップ

- **帯域外の使用量の突き合わせ:** Anthropic プールは権威ある使用量 API をポーリングできます（`usage_refresh_seconds`）。このブランチは ChatGPT バックエンドの非公開・未文書化の usage API をポーリングしないため、Codex のクォータ状態はここではレスポンスヘッダーから更新されます。帯域外 Codex ポーラーは #430 用に確保されています。
- **admin web でのプロビジョニング:** オプトインの[管理サーフェス](/ja/guides/admin-remote-provisioning/)は、ブラウザーで ChatGPT OAuth を実行し、リフレッシュ可能な Codex アカウントを保存し、共有プールのテーブルに表示し、報告された 5h/7d の使用量を表示できます（Codex には相当するものがないため `7d_oi` は空のままです）。

アカウントプールの内部仕様の全体は [M10 の挙動仕様](https://github.com/pleaseai/shunt/blob/main/docs/m10-codex-multi-account.md)を、単一アカウントのセットアップ、モデルルーティング、エフォート/コンテキストの設定については [ChatGPT / Codex ガイド](/ja/guides/codex/)を参照してください。
