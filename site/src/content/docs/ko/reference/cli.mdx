## `shunt run`

게이트웨이를 시작합니다. `run`은 기본 서브커맨드이므로, 맨 `shunt`만으로도 동작합니다.

```bash
shunt run
shunt run --config /path/to/shunt.toml
```

시작 시 바인딩된 주소(기본 `127.0.0.1:3001`)와 함께 `shunt listening`을 로깅합니다. 로그 상세도는 `RUST_LOG`로 설정하세요, 예: `RUST_LOG=shunt=debug shunt run`.

`--config` 없이 shunt는 `./shunt.toml` → `~/.config/shunt/shunt.toml` → `$HOMEBREW_PREFIX/etc/shunt.toml` 순서로 검색합니다; `--config`를 사용하면 파일이 없는 것은 오류입니다. [구성](/ko/guides/configuration/)을 참고하세요.

Homebrew로 설치했다면 백그라운드 서비스로 실행할 수도 있습니다: `brew services start shunt`. 자세한 내용은 [설치](/ko/getting-started/installation/#백그라운드-서비스로-실행하기)를 참고하세요.

## `shunt check`

해석된 구성을 검증하고 종료합니다(`shunt --check`도 동작):

```bash
shunt check
# -> config ok
```

구체적인 오류를 보고합니다: 잘못된 bind 주소, 라우트의 알 수 없는 프로바이더, 누락된 `api_key_env`, 잘못된 `base_url`, 잘못된 어댑터/인증 조합.

## `shunt init`

기존 디렉터리에 starter `shunt.toml`을 생성합니다. 이 명령은 해당 파일 하나만 쓰며, 아무것도 설치하거나 네트워크에 접근하지 않습니다.

```bash
shunt init
shunt init --upstream codex --upstream kimi
shunt init --root /path/to/project
shunt init --force
```

Upstream을 지정하지 않으면 starter 전체가 주석으로 구성되어 shunt의 기본 passthrough 설정으로 로드됩니다. `--upstream`을 반복하면 failover 순서대로 preset 항목을 추가합니다. 사용할 수 있는 이름은 `anthropic`, `codex`, `openai`, `xai`, `grok`, `kimi`, `cursor`, `kimi-code`입니다. Starter는 `server.default_provider`를 설정하지 않으므로 매핑되지 않은 트래픽은 기본 Anthropic passthrough를 유지합니다. Preset을 지정하면 생성된 파일이 `shunt check`를 통과하면서도 이 fallback을 유지하도록 마지막에 `anthropic` passthrough upstream이 자동으로 추가됩니다(직접 `anthropic`을 지정한 경우는 제외).

Root의 기본값은 현재 디렉터리이며 이미 존재해야 합니다. 그 안에 `shunt.toml`, `shunt.yaml`, `shunt.yml` 중 하나가 있으면 `--force` 없이는 아무것도 쓰지 않고 중단합니다. 강제 init은 `shunt.toml`만 덮어씁니다. YAML variant는 그대로 남고, config discovery에서는 새 TOML 파일이 우선합니다.

## `shunt add`

코딩 에이전트용 내장 Markdown blueprint를 가져옵니다. Blueprint는 설치 프로그램이 아니라 구현 가이드입니다. 이 명령은 파일을 수정하거나 설치하거나 네트워크에 접근하지 않습니다.

```bash
shunt add                                      # 두 blueprint kind 모두 나열
shunt add upstream                             # 이름이 있는 upstream 가이드 나열
shunt add upstream kimi --print                # 가이드 하나 출력
shunt add upstream https://example.com/docs    # 호환 endpoint 조사
shunt add provider https://example.com/docs    # 소스 코드 통합 조사
```

Kind는 `upstream`(제공되는 preset 또는 호환 endpoint 구성)과 `provider`(새 provider protocol 지원 기여)입니다. 알려진 upstream slug나 alias는 이름이 있는 가이드를 가져옵니다. 절대 `http://` 또는 `https://` URL은 해당 kind의 일반 research 가이드에 삽입되며, 상대 경로는 거부됩니다.

Blueprint Markdown은 에이전트로 바로 파이프할 수 있도록 항상 stdout으로 출력됩니다. `--print`는 그 의도를 명시하고 대화형 stderr hint를 억제하지만 stdout 내용은 바꾸지 않습니다.

```bash
shunt add upstream kimi --print | claude
```

## `shunt token`

Claude 구독 OAuth 토큰을 **stdout**으로 출력하며(로그는 stderr로), Claude Code의 `apiKeyHelper`에 연결되도록 설계되었습니다. 두 가지 모드:

- **정적** — `SHUNT_GATEWAY_TOKEN` 또는 `CLAUDE_CODE_OAUTH_TOKEN`이 설정되어 있으면, 그 값을 변경 없이 그대로 출력합니다. `claude setup-token` 값을 가리키게 하면 아무것도 갱신되지 않습니다.
- **자동 갱신** — 그렇지 않으면 `~/.claude/.credentials.json`을 읽고(경로는 `CLAUDE_CREDENTIALS`로 오버라이드), `claudeAiOauth` 액세스 토큰을 반환하며, `expiresAt` 5분 이내일 때 `platform.claude.com/v1/oauth/token`에 대해 갱신하여(Claude Code가 사용하는 것과 동일한 grant), 새 토큰을 `0600`으로 원자적으로 다시 쓰고 다른 모든 필드를 보존합니다. 갱신은 엔드포인트의 rate limit을 존중하기 위해 실제 만료 시에만 일어납니다.

```json
// ~/.claude/settings.json
{
  "apiKeyHelper": "/path/to/shunt token"
}
```

이것이 필요한 경우는 [Claude Code 연결](/ko/guides/connect-claude-code/#2-choose-the-anthropic-credential)을 참고하세요.

## `shunt gateway login`

[`[server.gateway]`](/ko/guides/gateway-login/)가 활성화된 shunt 배포에 이 머신을 로그인시킵니다. Claude Code의 `/login`이 사용하는 것과 동일한 OAuth device flow입니다. 이것은 게이트웨이의 **클라이언트** 쪽이며, `shunt login <provider>`와 `shunt token`은 그대로 유지되어 여전히 shunt 자신을 업스트림에 인증합니다.

```bash
shunt gateway login https://gateway.example.com
shunt gateway login https://gateway.example.com --manual   # 브라우저를 열지 않고 URL만 출력
```

shunt는 배포의 `/.well-known/oauth-authorization-server` 문서를 읽어 거기서 광고된 엔드포인트를 사용하고, 확인용 URL과 짧은 사용자 코드를 출력한 뒤 브라우저를 열고, 게이트웨이의 `/device` 페이지에서 승인할 때까지 폴링합니다. discovery가 `404`를 반환한다면 대개 그 배포에 `[server.gateway]` 섹션이 없다는 뜻입니다. discovery와 device code 요청에는 각각 상한이 있어, 연결만 수락하고 응답하지 않는 배포는 터미널을 무한정 붙잡는 대신 타임아웃으로 보고됩니다. 그 뒤의 승인 폴링은 기다리는 것이 본래 역할이므로 같은 방식으로 제한하지 않습니다. 루프백이 아닌 평문 `http://` URL도 허용되지만 경고가 출력됩니다 — device code와 refresh token이 암호화되지 않은 채 전송되기 때문이며, 이는 이번 로그인에 한정되지 않습니다. 이후의 모든 토큰 갱신도 같은 전송 경로를 사용하며, `shunt gateway token`은 실제로 갱신을 수행할 때마다 같은 경고를 다시 출력합니다(네트워크 호출이 없는 캐시 토큰 반환 시에는 출력하지 않습니다).

배포가 돌려주는 응답에는 두 가지 하한이 적용됩니다. shunt는 discovery 문서가 `https`로, 또는 루프백 주소에 대해 `http`로 광고한 엔드포인트에만 device code와 refresh token을 POST합니다. 그 외의 엔드포인트는 자격 증명을 받는 대신 discovery 단계에서 이름과 함께 실패합니다. 또한 확인용 URL은 `http` 또는 `https`일 때만 자동으로 열립니다 — 그 문자열은 shunt가 아니라 게이트웨이가 고르므로, 다른 스킴이면 열지 않은 이유와 함께 출력하고 따라갈지 여부는 사용자가 판단합니다.

세션은 `~/.shunt/gateway/session.json`에 저장되며(`SHUNT_GATEWAY_SESSION_FILE`로 오버라이드), 소유자 전용으로 기록됩니다: `0700` 디렉터리 안의 `0600` 파일.

## `shunt gateway token`

게이트웨이 액세스 토큰을 **stdout**으로만 출력합니다 — 모든 메시지와 경고, 힌트는 stderr로 갑니다 — 그래서 Claude Code의 `apiKeyHelper`에 그대로 연결됩니다:

```json
// ~/.claude/settings.json
{
  "apiKeyHelper": "/path/to/shunt gateway token"
}
```

이것은 업스트림 Claude 구독 토큰을 출력하는 [`shunt token`](#shunt-token)과는 **다른 헬퍼**입니다. 둘은 서로의 저장소를 읽지 않으며, 이름이 비슷한 `SHUNT_GATEWAY_TOKEN` 변수는 이 명령이 아니라 `shunt token`의 것입니다.

저장된 토큰은 만료 5분 전까지 그대로 제공되고, 그 이후 갱신됩니다. 게이트웨이의 refresh token은 회전하며 일회용이므로, 갱신은 배타적 파일 잠금 아래에서 실행되고 잠금을 획득한 뒤 세션을 다시 읽습니다: 여러 Claude Code 세션이 동시에 헬퍼를 호출해도 갱신은 한 번만 일어나며, 회전 계열 전체를 무효화하는 재사용이 발생하지 않습니다.

잠금도 갱신도 무한정 기다리지 않습니다. 게이트웨이와의 각 왕복은 물론 잠금 대기에도 상한이 있습니다 — 연결은 수락하고 응답하지 않는 배포가 잠금을 쥔 채로 그 머신의 다른 모든 `apiKeyHelper`를 아무 설명 없이 멈춰 세우기 때문입니다. 상한을 넘기면 명령이 실패하면서 잠금 파일 경로를 알려줍니다.

5분 버퍼에 들어갔다는 것은 갱신이 **필요한 시점**이라는 뜻이지 **필수**라는 뜻은 아닙니다. 캐시된 토큰이 아직 실제로 유효한 상태에서 갱신이 실패하면, 짧은 네트워크 장애를 인증 실패로 바꾸는 대신 stderr에 경고를 남기고 그 토큰을 제공합니다. 실제로 만료된 뒤에는 명령이 실패합니다. Claude Code의 헬퍼 검증기가 거부할 토큰 — 공백 없는 출력 가능 ASCII 1~16384자가 아닌 값 — 은 아무 설명 없이 인증을 실패시키도록 출력되는 대신, 게이트웨이를 지목하는 진단과 함께 여기서 거부됩니다. `shunt gateway logout`은 세션과 함께 잠금 파일도 제거합니다.

## `shunt gateway claude`

설정 파일을 편집하지 않고 Claude Code를 게이트웨이에 연결해 실행합니다:

```bash
shunt gateway claude
shunt gateway claude -p 'summarize this repo' --model opus
```

저장된 세션의 게이트웨이를 `ANTHROPIC_BASE_URL`로 가리키고 `apiKeyHelper`를 이 바이너리의 절대 경로 + `gateway token`으로 설정한 인라인 `--settings` 문서와 함께 `claude`를 실행합니다. 이 문서는 해당 프로세스 하나에만 적용됩니다: `~/.claude/settings.json`은 전혀 수정되지 않으며, 셸에 이미 export된 `ANTHROPIC_BASE_URL`보다 우선합니다(Claude Code 2.1.234 기준 실측).

`claude` 뒤의 인자는 모두 그대로 전달됩니다. 인자 목록 맨 앞에 올 때만 두 가지 예외가 있습니다: `--help`는 shunt의 도움말을 출력하고, `--config`는 shunt의 전역 옵션에 조용히 삼켜지는 대신 오류로 거부됩니다. 둘 중 어느 것이든 `claude`로 보내려면 `--` 뒤에 두세요:

```bash
shunt gateway claude -- --config /path/to/claude/config
```

자격 증명이 `apiKeyHelper`를 통해 전달되므로 세션은 로그인된 게이트웨이 세션이 되지 않고 Claude Code의 일반적인 first-party 모드로 유지됩니다 — 토큰이 어느 자격 증명 슬롯에 도착하는지가 모드를 결정합니다. 무엇을 포기하는지는 [게이트웨이 로그인](/ko/guides/gateway-login/#터미널에서-로그인하기)을 참고하세요.

## `shunt gateway logout`

저장된 세션을 삭제합니다. 멱등적입니다 — 이미 없는 세션을 삭제해도 성공합니다.

```bash
shunt gateway logout
```

## `shunt login claude`

세 가지 모드 중 하나로 shunt가 관리하는 Anthropic 풀 계정을 만듭니다:

```bash
# Full OAuth: shunt가 새 갱신 가능 로그인을 발급받아 저장합니다(권장).
shunt login claude --name primary --mode oauth

# 현재의 갱신 가능한 Claude Code 로그인을 가져옵니다.
shunt login claude --name imported --mode import

# Claude의 1년짜리 추론 전용 setup-token 플로우를 실행합니다.
shunt login claude --name ci --mode setup-token
```

TTY에서 `--mode`를 생략하면 shunt는 `oauth`, `import`, `setup-token` 중 하나를 선택하도록 묻고 OAuth를 기본 권장값으로 사용합니다. 비대화형 입력에서는 기존 `import` 기본값을 유지합니다. `--long-lived`는 `--mode setup-token`의 deprecated alias로 남아 있습니다.

`--mode oauth`는 shunt의 full-scope PKCE 인가 플로우를 실행하고 access token과 refresh token을 모두 저장합니다. 기본적으로 shunt는 `127.0.0.1`에 임시 리스너를 바인딩하고 인가 URL을 연 뒤, 브라우저가 `http://127.0.0.1:<port>/callback`으로 돌아오면 완료합니다. 브라우저를 열 수 없거나 리스너를 시작할 수 없거나 5분 안에 callback이 오지 않으면 숨겨진 수동 붙여넣기 플로우로 fallback합니다. SSH나 headless 환경에서는 `--manual`로 바로 수동 플로우를 사용할 수 있습니다:

```bash
shunt login claude --name remote --mode oauth --manual
```

`--mode import`는 `~/.claude/.credentials.json`(또는 `CLAUDE_CREDENTIALS`)을 `~/.shunt/accounts/claude/<name>.json`으로 복사합니다. refresh token을 보존하고 Claude Code 전역 구성의 현재 계정 UUID를 연결하며, shunt는 Claude Code의 원본 파일을 변경하지 않고 이 비공개 복사본을 갱신합니다.

`--mode setup-token`은 `claude setup-token`과 같은 1년짜리 추론 전용 PKCE 플로우를 실행합니다. 브라우저에서 승인한 뒤 표시된 인가 코드를 shunt의 숨겨진 프롬프트에 붙여 넣으세요. shunt는 코드를 직접 교환하고 opaque token과 발급 계정 UUID를 모두 저장하며 토큰을 출력하지 않습니다.

파일은 Unix에서 `0600` 권한으로 원자적으로 기록되며, 부모 디렉터리가 없으면 `0700` 권한으로 새로 만듭니다. `SHUNT_CLAUDE_ACCOUNTS_DIR`로 스토어 디렉터리를 재정의할 수 있으며, 이미 존재하는 디렉터리를 가리키는 경우에는 그 디렉터리의 기존 권한이 그대로 유지되고 shunt가 강제로 `0700`으로 바꾸지는 않습니다. 같은 이름을 다시 사용하면 파일이 교체됩니다. 기존 외부 setup token은 발급 후 계정 UUID를 복구할 수 없으므로 여전히 `token_env`와 명시적 `uuid`가 필요합니다.



<Aside type="caution" title="갱신 가능 로그인당 하나의 owner">

OAuth provider는 shunt가 access token을 갱신할 때 refresh token도 회전할 수 있습니다. 같은 갱신 가능 credential 파일을 여러 shunt 프로세스에서 실행하거나, 활성 스토어 파일을 다른 호스트로 복사해 독립적으로 실행하지 마세요. 한쪽의 첫 갱신이 다른 복사본을 무효화할 수 있습니다. 프로세스마다 별도로 프로비저닝하거나, 공유 정적 credential이 필요한 경우 갱신 불가능한 setup token을 사용하세요.

</Aside>



결과는 이름만 있는 풀 항목으로 참조하거나, provider의 계정 목록을 비워 모든 스토어 파일을 스캔할 수 있습니다:

```toml
[[providers.anthropic.accounts]]
name = "primary"
```

## `shunt login kimi`

Kimi Code의 device-authorization([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628)) OAuth 플로우를 실행하고 갱신 가능한 credential을 저장합니다:

```bash
shunt login kimi --name <account-name>
```

`--name`은 필수입니다. 생략하면 `` `shunt login kimi` requires --name <account-name> `` 오류로 실패합니다. Kimi Code OAuth 토큰은 항상 갱신 가능하므로 `--mode`와 `--long-lived`는 거부됩니다. `--manual`은 claude 전용입니다.

로그인 시 해당 계정의 `X-Msh-Device-Id`가 한 번 생성되어 이후의 모든 갱신에서 재사용되므로, 계정은 Kimi에 안정적인 디바이스 신원을 제시합니다. 안정적인 upstream 계정 식별자를 담은 Kimi 로그인 응답은 지금까지 관측된 적이 없으므로, 스캔된 항목의 풀 신원은 그 자체의 파일명이 됩니다.

파일은 Unix에서 `0600` 권한으로 원자적으로 기록됩니다. shunt가 생성하는 스토어 디렉터리는 `0700`으로 만들어집니다. `SHUNT_KIMI_ACCOUNTS_DIR`로 스토어 디렉터리를 재정의할 수 있으며, 같은 이름을 재사용하면 파일이 교체됩니다.

결과는 `auth = "kimi_oauth"`를 사용하는 provider에서 소비되며, 이는 `kind = "anthropic"`이고 base URL이 `kimi.com`일 때만 유효합니다. 이름만 있는 풀 항목으로 참조합니다:

```toml
[[providers.kimi-code.accounts]]
name = "primary"
```

config는 provider를 `[[upstreams]]` 또는 `[providers.*]` 중 한 형식으로만 선언하며 둘을 함께 쓸 수 없습니다. `[[upstreams]]` config에서는 대신 auth 맵에 계정을 지정하세요: `auth = { mode = "kimi_oauth", accounts = ["primary"] }`.

Kimi는 갱신할 때마다 refresh token을 회전시키며, 발급되는 access token 수명도 약 15분으로 짧아 갱신이 자주 일어납니다. 따라서 위의 "갱신 가능한 로그인은 프로세스 하나만" 원칙이 그대로 강하게 적용됩니다. 하나의 Kimi 계정 파일을 여러 shunt 프로세스가 공유하면 첫 갱신에서 서로를 무효화합니다.

전체 upstream 구성은 [Kimi](/ko/providers/kimi/#kimi-code-oauth-subscription)를 참고하세요.

## Anthropic 계정 풀 인증

`auth = "claude_oauth"`인 Anthropic provider에서 계정은 이름만 있는 스토어 항목, `credentials = "~/.claude/.credentials.json"`, 또는 `token_env = "YOUR_ENV_NAME"`을 사용할 수 있습니다. 스토어 항목은 위의 Full OAuth, Claude Code 로그인 가져오기, setup-token 플로우 중 하나로 만들 수 있습니다. 전체 구성과 failover 규칙은 [Anthropic 멀티 계정](/ko/guides/anthropic-multi-account/)을 참고하세요.

## 환경 변수

| 변수 | 효과 |
| :-- | :-- |
| `SHUNT_*`(예: `SHUNT_SERVER__BIND`) | 임의의 구성 키를 오버라이드; `__`는 중첩 키를 구분 |
| `RUST_LOG` | 로그 필터, 예: `shunt=debug` |
| `SHUNT_CLIENT_TOKENS` | [`[server.auth]`](/ko/guides/shared-gateway/)용 클라이언트 토큰(이름은 `tokens_env`로 구성 가능) |
| `SHUNT_GATEWAY_TOKEN` / `CLAUDE_CODE_OAUTH_TOKEN` | `shunt token`용 정적 토큰 |
| `SHUNT_GATEWAY_SESSION_FILE` | `shunt gateway` 명령들이 사용하는 대체 세션 파일(기본 `~/.shunt/gateway/session.json`); 위의 `SHUNT_GATEWAY_TOKEN`과는 무관 |
| `CLAUDE_CREDENTIALS` | `shunt token` 및 갱신 가능한 `shunt login claude` 가져오기용 대체 credential 파일 경로 |
| `SHUNT_CLAUDE_ACCOUNTS_DIR` | shunt가 관리하는 Claude 계정 스토어의 대체 디렉터리 |
| `SHUNT_KIMI_ACCOUNTS_DIR` | shunt가 관리하는 Kimi Code 계정 스토어의 대체 디렉터리 |
| `token_env`로 지정한 계정별 변수 | Anthropic `claude_oauth` 풀 항목의 setup token; 변경 없이 그대로 사용 |
| `OPENAI_API_KEY` | `openai` 프로바이더용 기본 키 env(프로바이더별로 `api_key_env`를 통해) |
