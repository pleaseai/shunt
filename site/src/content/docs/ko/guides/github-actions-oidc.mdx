공유 게이트웨이를 호출해야 하는 워크플로는 보통 GitHub secrets에 클라이언트 토큰을 저장합니다. 이 가이드는 그 secret을 없앱니다. 모든 Actions 잡은 GitHub에서 OIDC 토큰을 요청할 수 있고, shunt의 [`[[server.auth.jwt]]`](/ko/guides/shared-gateway/#자체-identity-provider의-jwt-검증) 검증기는 이를 직접 받을 수 있습니다. 게이트웨이에서 새로 실행할 것이 없고, GitHub에 장기 자격 증명을 저장하지도 않습니다.

shunt는 GitHub이 공개한 키로 토큰 서명을 검증한 다음, **클레임**으로 인가합니다. 즉 잡이 어느 조직과 저장소에서 실행되는지를 봅니다. 이미 Google Cloud를 운영하고 있고 이메일 형태의 신원을 원한다면 끝부분의 [Google 서비스 계정 대안](#대안-google-서비스-계정)을 참고하세요.

## GitHub이 토큰에 넣는 것

GitHub Actions OIDC 토큰에는 `email` 클레임이 없습니다. 여기서 중요한 클레임은 다음과 같습니다(GitHub의 [OIDC 레퍼런스](https://docs.github.com/en/actions/reference/security/oidc) 참고).

| 클레임 | 값 |
| :-- | :-- |
| `iss` | `https://token.actions.githubusercontent.com` |
| `aud` | 기본값은 저장소 소유자의 URL이며, 잡은 임의의 문자열을 요청할 수 있습니다 |
| `sub` | `repo:`로 시작합니다. 예: `repo:my-org/my-repo:ref:refs/heads/main`, `...:pull_request`, `...:environment:prod`, `...:ref:refs/tags/v1` |
| `repository`, `repository_id` | `my-org/my-repo`와 그 숫자 id |
| `repository_owner`, `repository_owner_id` | 조직 또는 사용자와 그 숫자 id |
| `ref`, `environment`, `job_workflow_ref` | 브랜치 또는 태그 ref, 환경 이름, 재사용 워크플로 경로 |

`sub` 형식은 저장소마다 같지 않습니다. 2026년 7월 15일 이후에 만들어진 저장소와 그 이후 이름이 바뀌거나 이전된 저장소는 `repo:OWNER@OWNER-ID/REPO@REPO-ID:...` 형식을 쓰고, 그 밖의 이전 저장소는 옵트인하지 않는 한 `repo:OWNER/REPO:...`를 유지하며, 조직이나 저장소 관리자는 `sub`를 완전히 바꿀 수도 있습니다(예: `repository_owner:my-org`). 아래 설정이 `sub`가 아니라 숫자 id 클레임으로 인가하는 이유입니다.

## shunt 설정

```toml
[server.auth]
# No static tokens needed once a JWT issuer is configured.
tokens_env = "SHUNT_CLIENT_TOKENS"

[[server.auth.jwt]]
issuer = "https://token.actions.githubusercontent.com"
audience = ["https://shunt.example.com"]                 # a string dedicated to shunt; the workflow requests the same one
require = { repository_owner_id = "1234567", repository_id = ["7654321", "7654322"] }
identity_claim = "repository"
```

GitHub CLI로 id를 확인합니다.

```bash
gh api orgs/my-org --jq .id              # repository_owner_id (users/<name> for a personal account)
gh api repos/my-org/my-repo --jq .id     # repository_id
```

항목을 읽는 방법은 다음과 같습니다.

- **인가하는 것은 `require`입니다.** 어떤 GitHub 저장소든 임의의 `aud`로 토큰을 요청할 수 있으므로 `audience`가 일치한다는 사실은 아무것도 증명하지 않습니다. 다른 서비스용으로 발급된 토큰이 여기서 재사용되는 것을 막을 뿐입니다. `require`는 클레임 이름을 문자열 또는 배열에 매핑합니다. 나열된 모든 클레임은 JSON 문자열로 존재해야 하고 값 중 하나와 정확히(대소문자 구분) 같아야 합니다. 클레임 사이는 AND, 한 클레임 안의 값들은 any-of입니다. GitHub 토큰에서 id는 문자열이므로 따옴표로 감싸세요.
- **이름이 아니라 숫자 id를 쓰세요.** 조직과 저장소 이름은 변경, 삭제된 뒤 다른 사람이 다시 등록할 수 있지만 id는 그럴 수 없습니다. 여러 저장소를 허용하려면 `repository_id` 값을 여러 개 나열합니다.
- **`identity_claim = "repository"`**는 호출자 신원을 `my-org/my-repo`로 만들며, 로그와 사용량 귀속에 나타나는 값입니다. 이것은 레이블일 뿐 인가 수단이 아닙니다(인가는 id가 합니다). 항목에 이메일 규칙이 없으므로 여기서는 필수이고, 값은 비어 있지 않은 256바이트 이하의 문자열이어야 합니다. `sub`를 신원으로 쓰지 마세요. 브랜치 구간은 호출자가 정할 수 있습니다.
- **`email_verified` 검사는 적용되지 않습니다.** 항목에 이메일 규칙이 없고, 신원 클레임이 `email`이 아니며, `require`가 `email`을 지정하지 않기 때문입니다.

더 좁히려면 `require`에 정확히 일치하는 클레임을 추가하세요. 예를 들어 `ref = "refs/heads/main"` 또는 `environment = "production"`입니다. 접두사 매칭과 달리 `refs/heads/main-evil` 같은 더 긴 이름으로는 만족시킬 수 없고, `sub` 형식에도 의존하지 않습니다.

`subject_prefix`도 사용할 수 있지만(문자열 또는 배열이며, `sub`가 그중 하나로 시작해야 함) 주의가 필요합니다. 접두사는 구분자에서 끝내세요. `repo:my-org`가 아니라 `repo:my-org/`입니다. 앞의 것은 `repo:my-org-evil/...`에도 일치합니다. 또한 위의 두 가지 `sub` 형식 때문에 `repo:my-org/my-repo:` 같은 이름 기반 접두사는 immutable 형식을 쓰는 저장소와 일치하지 않습니다. `require` 위에 얹는 추가 제한으로만 쓰고, 유일한 규칙으로 쓰지 마세요.

JWT는 `Authorization: Bearer`로만 받으며 업스트림으로 전달되지 않습니다. `[server.auth]`가 이미 게이트하는 라우트(자격 증명을 주입하는 `/v1/messages`, `GET /v1/models` 등 [게이팅되는 라우트](/ko/reference/configuration/#serverauthjwt-선택))에서는 신원이 로그와 사용량에 귀속됩니다. 패스스루 추론은 검사하지 않습니다. 호출자가 자신의 자격 증명으로 비용을 지불하기 때문입니다.

## 워크플로

잡에는 `id-token: write`가 필요합니다. 이 권한은 OIDC 토큰을 요청할 수 있게 할 뿐 다른 접근 권한은 주지 않습니다. 토큰은 러너 자체의 엔드포인트에서 가져오므로 서드파티 액션이 필요 없습니다.

```yaml
name: ask-claude
on:
  workflow_dispatch:

permissions:
  contents: read
  id-token: write          # lets the job request a GitHub OIDC token

jobs:
  ask:
    runs-on: ubuntu-latest
    env:
      SHUNT_URL: https://shunt.example.com
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - name: Get a GitHub OIDC token for shunt
        run: |
          token="$(curl -fsS -G \
            -H "Authorization: bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
            --data-urlencode "audience=$SHUNT_URL" \
            "$ACTIONS_ID_TOKEN_REQUEST_URL" | jq -r .value)"
          echo "::add-mask::$token"
          echo "SHUNT_TOKEN=$token" >> "$GITHUB_ENV"

      - name: Smoke test
        run: |
          curl -fsS "$SHUNT_URL/v1/models" \
            -H "Authorization: Bearer $SHUNT_TOKEN" | head -c 400

      - name: Run Claude Code
        run: |
          npm install -g @anthropic-ai/claude-code
          ANTHROPIC_BASE_URL="$SHUNT_URL" ANTHROPIC_AUTH_TOKEN="$SHUNT_TOKEN" \
            claude -p "Summarize the last commit."
```

`audience`는 shunt 항목의 `audience`와 같아야 합니다. `::add-mask::`는 토큰을 저장하기 전에 secret으로 등록하므로 로그에 나와도 가려집니다. 그래도 `echo`하거나 `set -x`로 실행하지 마세요. 포크에서 온 pull request는 토큰에 쓰기 권한을 받지 못하므로(GitHub이 읽기로 낮춥니다) 포크 pull request로 트리거된 잡은 대개 OIDC 토큰을 요청할 수 없습니다. `pull_request` 워크플로에서는 이 점을 염두에 두세요.

## 토큰 수명

OIDC 토큰은 bearer입니다. 만료될 때까지 사용할 수 있고 shunt는 폐기 상태를 보관하지 않습니다. GitHub 문서는 `exp`와 `iat`를 클레임으로 나열하지만 수명을 명시하지는 않습니다. GitHub 자체 엔터프라이즈 예시의 토큰은 `exp - iat`가 300초입니다. shunt는 `exp - iat`가 `max_token_age_seconds`(기본 `3600`)를 *초과*할 때만 거부하므로 기본값으로 받아들입니다. 긴 잡은 하나의 토큰을 잡 전체에서 들고 있지 말고, shunt를 호출하는 단계 전에 위와 같은 단계로 새 토큰을 요청하세요. Claude Code 세션 하나처럼 단일 프로세스는 시작할 때 받은 토큰을 계속 사용하며, 그 토큰이 만료되면 `401`을 받습니다. 토큰보다 오래 실행되는 세션에는 같은 방식으로 새 토큰을 요청하는 스크립트를 Claude Code의 `apiKeyHelper`로 설정하세요(요청 변수는 `id-token: write`가 있는 잡의 모든 단계에 설정됩니다). 이때 Claude Code는 `ANTHROPIC_AUTH_TOKEN` 없이 실행하세요. `ANTHROPIC_AUTH_TOKEN`이 설정되어 있으면 `apiKeyHelper`보다 우선하므로 세션이 만료된 토큰을 계속 씁니다.

## 문제 해결

**`401 authentication_error`.** shunt는 실패한 모든 검사에 같은 응답을 주므로, 디코딩한 토큰을 항목과 대조해 보세요.

| 검사 | 해결 |
| :-- | :-- |
| `aud`가 `audience`에 없음 | `audience` 쿼리 파라미터와 설정 값이 정확히 같아야 합니다 |
| `require` 클레임이 없거나 값이 다름 | 페이로드의 `repository_owner_id`, `repository_id`와 비교하세요. 문자열이어야 하고 저장소가 목록에 있어야 합니다 |
| `sub`가 `subject_prefix`로 시작하지 않음 | `sub` 형식(이름 기반, immutable, 사용자 지정)을 확인하고 접두사를 빼거나 고치세요 |
| `repository`(신원 클레임)가 없거나 비어 있거나 256바이트 초과 | 클레임은 비어 있지 않은 문자열이어야 합니다. `identity_claim` 철자를 확인하세요 |
| `iss`가 설정한 `issuer`와 다름 | GitHub Enterprise Cloud 엔터프라이즈는 고유 issuer `https://token.actions.githubusercontent.com/<enterprise-slug>`를 선택할 수 있습니다. 토큰에 담긴 값으로 `issuer`를 설정하세요 |
| `exp - iat`가 `max_token_age_seconds`보다 큼 | 토큰 수명보다 낮게 설정한 경우에만 해당합니다 |

**`api_error` 본문과 함께 `503`.** shunt가 GitHub의 키 집합을 가져오지 못했습니다. 자격 증명은 문제가 없습니다. 게이트웨이가 `https://token.actions.githubusercontent.com`에 접근할 수 있는지 확인하세요. 키 집합은 처음 사용할 때 가져오므로, 실패는 시작 시점이 아니라 첫 요청에서 드러납니다. [동시성 제한](/ko/guides/shared-gateway/#인바운드-동시성-제한)이 반환하는 `overloaded_error`와는 다릅니다.

**`ACTIONS_ID_TOKEN_REQUEST_URL`이 비어 있음.** 잡에 `id-token: write`가 없거나 포크에서 실행되고 있습니다.

**페이로드 확인.** 클레임(가운데 세그먼트)만 디코딩하고, 토큰 전체를 어디에도 붙여 넣지 마세요.

```bash
python3 -c 'import sys,json,base64; p=sys.stdin.read().strip().split(".")[1]; print(json.dumps(json.loads(base64.urlsafe_b64decode(p+"="*(-len(p)%4))),indent=2))' <<< "$SHUNT_TOKEN"
```

일회용 디버그 단계에서 실행하세요. 페이로드에는 secret이 없지만, 어떤 클레임이 검사와 어긋나는지 가장 빨리 볼 수 있는 방법입니다. 전체 키 목록은 [설정 레퍼런스](/ko/reference/configuration/#serverauthjwt-선택)를 참고하세요.

## 대안: Google 서비스 계정

이미 Google Cloud를 운영하고 있거나 이메일 주소 형태의 신원을 원한다면 이 경로를 쓰세요. 잡은 GitHub OIDC 토큰으로 Google Cloud에 자신을 증명하고, Google이 서비스 계정용 단기 ID 토큰을 발급하며, shunt는 `allowed_emails` 같은 이메일 규칙으로 그 ID 토큰을 받습니다. 어떤 저장소가 서비스 계정이 될 수 있는지는 shunt가 아니라 Google Cloud의 Workload Identity Federation 속성 조건(attribute condition)과 IAM 바인딩이 결정합니다.

IAM, Resource Manager, Service Account Credentials, Security Token Service API가 활성화된 프로젝트가 필요합니다.

```bash
PROJECT_ID="my-project"
PROJECT_NUMBER="$(gcloud projects describe "$PROJECT_ID" --format='value(projectNumber)')"
GITHUB_ORG="my-org"
GITHUB_REPO="my-org/my-repo"
SA_EMAIL="shunt-ci@${PROJECT_ID}.iam.gserviceaccount.com"

gcloud iam service-accounts create shunt-ci --project="$PROJECT_ID"   # needs no project roles

OWNER_ID="$(gh api "orgs/${GITHUB_ORG}" --jq .id)"
REPO_ID="$(gh api "repos/${GITHUB_REPO}" --jq .id)"

gcloud iam workload-identity-pools create github \
  --project="$PROJECT_ID" --location=global \
  --display-name="GitHub Actions"

gcloud iam workload-identity-pools providers create-oidc shunt \
  --project="$PROJECT_ID" --location=global \
  --workload-identity-pool=github \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository_id=assertion.repository_id,attribute.repository_owner_id=assertion.repository_owner_id" \
  --attribute-condition="assertion.repository_owner_id == '${OWNER_ID}'"

gcloud iam service-accounts add-iam-policy-binding "$SA_EMAIL" \
  --project="$PROJECT_ID" \
  --role="roles/iam.workloadIdentityUser" \
  --member="principalSet://iam.googleapis.com/projects/${PROJECT_NUMBER}/locations/global/workloadIdentityPools/github/attribute.repository_id/${REPO_ID}"

gcloud iam workload-identity-pools providers describe shunt \
  --project="$PROJECT_ID" --location=global --workload-identity-pool=github \
  --format='value(name)'                                              # -> workload_identity_provider

gcloud iam service-accounts describe "$SA_EMAIL" \
  --project="$PROJECT_ID" --format='value(uniqueId)'                  # -> authorized_parties
```

<Aside type="caution">

GitHub는 모든 조직에 하나의 issuer URL을 쓰므로, 다른 조직이 풀에 들어오지 못하게 막는 것은 `--attribute-condition`입니다. 이 조건 없이 프로바이더를 만들지 마세요. 그러면 어떤 GitHub 저장소든 풀에 토큰을 제시할 수 있습니다. Google은 이름 대신 숫자 `*_id` 클레임을 쓰도록 권장합니다. IAM 바인딩은 조직을 저장소 하나로 좁힙니다. `principalSet` 멤버를 `attribute.repository_owner_id/...`로 넓히면 조직의 모든 저장소가 게이트웨이를 호출할 수 있습니다. 액션이 ID 토큰을 발급하는 데는 `roles/iam.workloadIdentityUser`로 충분합니다. 이 역할에 `iam.serviceAccounts.getOpenIdToken`이 포함되어 있기 때문이며, `roles/iam.serviceAccountOpenIdTokenCreator`도 사용할 수 있습니다.

</Aside>

```toml
[[server.auth.jwt]]
issuer = "https://accounts.google.com"
audience = ["shunt-ci"]                                        # any string; the workflow asks for the same one
allowed_emails = ["shunt-ci@my-project.iam.gserviceaccount.com"]
authorized_parties = ["112010400000000710080"]                 # the service account's uniqueId
```

- **`allowed_emails`**: `email_domains = ["my-project.iam.gserviceaccount.com"]`보다 정확한 주소를 권장합니다. 도메인 규칙은 프로젝트의 어떤 서비스 계정이 발급한 ID 토큰이든 받아들입니다. 호출자 신원은 이 이메일입니다.
- **`authorized_parties`는 필수입니다.** Google은 `azp`(그리고 `sub`)에 서비스 계정의 숫자 고유 ID를 넣고 `aud`에는 여러분의 audience 문자열을 넣습니다. shunt는 `azp`가 있으면 항상 검사하고 허용 집합의 기본값을 `audience`로 두기 때문에, 이 키가 없으면 모든 토큰이 `401`로 거부됩니다.
- 토큰의 `email_verified`는 이메일을 포함해 발급할 때만 `true`이므로, 워크플로에서 `id_token_include_email: true`를 설정해야 합니다.

```yaml
permissions:
  contents: read
  id-token: write

jobs:
  ask:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2
      - id: auth
        uses: google-github-actions/auth@7c6bc770dae815cd3e89ee6cdf493a5fab2cc093 # v3.0.0
        with:
          workload_identity_provider: projects/123456789/locations/global/workloadIdentityPools/github/providers/shunt
          service_account: shunt-ci@my-project.iam.gserviceaccount.com
          create_credentials_file: false
          token_format: id_token
          id_token_audience: shunt-ci          # must equal `audience` in shunt
          id_token_include_email: true         # adds the email and email_verified claims

      - name: Run Claude Code
```

액션은 ID 토큰을 마스킹된 secret으로 등록합니다. 수명: Google은 서비스 계정 ID 토큰의 유효 시간을 1시간으로 문서화하고 있고, 액션의 README는 최대 10분이며 변경할 수 없다고 적고 있습니다. 어느 쪽이든 기본 `max_token_age_seconds`를 통과하지만 더 짧은 쪽을 기준으로 계획하고, 긴 단계 전에는 auth 단계를 다시 실행하세요. `401`이 나면 위의 디코딩 스니펫을 그대로 쓸 수 있습니다. `iss`, `aud`, `azp`(= `sub` = 고유 ID), `email`, `email_verified: true`가 보여야 하며, `aud`는 `audience`와, `azp`는 `authorized_parties`와, `email`은 `allowed_emails`와 대조하세요. 자신의 머신에서 비슷한 토큰을 얻으려면 서비스 계정을 가장(impersonate)하세요. 사용자 계정에 해당 서비스 계정에 대한 `roles/iam.serviceAccountOpenIdTokenCreator`가 필요합니다.

```bash
SHUNT_TOKEN="$(gcloud auth print-identity-token \
  --impersonate-service-account="$SA_EMAIL" --audiences=shunt-ci --include-email)"
```
