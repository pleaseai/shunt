shunt의 [스테이지 라우터](/ko/guides/stage-router/)는 자체 스코어링을 만들지
않았습니다. [NVIDIA-NeMo/Switchyard][sy]의 라우팅 라이브러리
[`switchyard-libsy`][libsy]에 의존합니다 — "각 LLM 호출을 그래도 해낼 수 있는 가장
저렴한 모델로 라우팅한다"를 내건 프로젝트입니다.

이 문서는 통합 기록입니다. shunt가 Switchyard의 어느 부분을 쓰고 어느 부분을
의도적으로 쓰지 않는지, 공개된 수치가 실제로 무엇을 측정한 것인지, 알고리즘이 한
턴을 어떻게 판정하는지를 다룹니다. 기능을 켜는 방법만 필요하다면
[스테이지 라우터 가이드](/ko/guides/stage-router/)가 더 짧습니다.

[libsy]: https://github.com/NVIDIA-NeMo/Switchyard/tree/3ddea9d30174ad835cf505a93617ba251c8eb8dd/crates/libsy
[sy]: https://github.com/NVIDIA-NeMo/Switchyard

## shunt가 가져온 것

Switchyard는 게이트웨이 한 벌을 제공합니다. 프록시 서버, 프로바이더 중립 프로토콜,
요청/응답 번역, LLM 판정자 분류기, 에스컬레이션, 서브에이전트 라우팅까지. shunt는
이미 게이트웨이이므로 스코어러와, 옵트인 테이블 뒤의 판정자 분류기, 그 경계에서만 쓰는
번역 코덱을 가져오고 나머지는 두고 옵니다.

| Switchyard 구성 요소 | shunt에서 |
| :-- | :-- |
| `switchyard-libsy` 스테이지 스코어러 | **사용** — 업스트림 `main`의 검토된 리비전에 고정 |
| `switchyard-protocol` | libsy의 의존성으로 딸려옴. shunt는 `Request`를 만들지 않음 |
| `switchyard-translation` | **라우팅 경계에서만 사용** — 판정 요청과 그 응답의 중립 ⇄ Anthropic 변환. Anthropic → Responses 와이어 변환은 계속 shunt 자신의 `src/model/responses_request.rs`가 맡음 |
| `switchyard-server` | **미사용** — shunt가 곧 서버 |
| LLM 분류기 / 판정자 | **항목별 옵트인** — `stage_router`의 [`[models.router.classifier]`](/ko/guides/stage-router/#판정-모델-폴백). 신호가 결론을 내지 못한 턴에서만 호출됨. [아래](#핫-패스에-llm-판정자를-두지-않는다) 참고 |
| 에스컬레이션 라우팅(턴 중간) | **미사용** — shunt의 post-2xx 무재생 규칙과 충돌 |
| 핸드오프 노트 | **사용** — [`[models.router.handoff_notes]`](/ko/reference/configuration/#modelsrouterhandoff_notes-선택) |
| 어드바이저 게이트, 서브에이전트 라우팅 | **미사용** |

결합점은 함수 호출 하나가 전부입니다. shunt는 파싱된 Anthropic Messages 본문에서
libsy의 `ToolSignals` 구조체를 직접 채우고 `pick_tier`를 호출합니다. 그 구조체의
모든 필드가 `pub`이라 사이에 번역 계층이 들어가지 않습니다.

의존성은 crates.io 릴리스가 아니라 업스트림 `main`의 **불변 리비전에 건 git 핀**이고,
`branch` 키 없이 `rev`만 씁니다 — shunt의 `tungstenite` 핀 두 개와 같은 형태입니다.
따라서 버전을 올리는 일은 검토를 거친 diff이지, 무관한 `cargo update`가 할 수 있는
일이 아닙니다. `0.2.0`은 유일한 공개 릴리스이고 `main`은 이미 갈라졌습니다. 스테이지
스코어링 너머의 알고리즘 — advisor gate, composite 라우팅, 서브에이전트 라우팅,
tool semantics, handoff note — 은 `main`에만 있습니다. API를 확인할 때는 레지스트리
소스도, 움직이는 GitHub 기본 브랜치도 아니라 cargo가 해석한 체크아웃을 읽으세요.

### 학습형 프리필 라우터

업스트림에서 가져온 조각이 하나 더 있는데, 조건이 다릅니다. 가장 최근 사용자 턴을 채점해
타깃을 고르는 학습형 분류기 `prefill_router`입니다. 이것은 기본으로 꺼져 있는
**`prefill-router` 카고 피처**를 켜고 빌드한 바이너리에서만 쓸 수 있습니다.

이유는 그 크레이트의 정체입니다. 업스트림의 `crates/prefill-router`는 PyO3로 Python을
임베드하므로, 빌드는 libpython을 링크하고 실행에는 `torch`, `transformers`, `numpy`,
`accelerate`를 import할 수 있는 환경과 디스크에 놓인 라우터 체크포인트가 필요합니다.
업스트림도 같은 이유로 카고 피처 뒤에 둡니다. shunt의 릴리스 워크플로는 이 피처를 켜지
않으므로 **미리 빌드된 릴리스 바이너리와 Homebrew 포뮬러에는 들어 있지 않습니다.**
소스에서 `cargo build --release --features prefill-router`로 빌드하는 것이 유일한 방법이고,
피처가 없는 바이너리는 이 타입을 지정한 설정을 로드하지 못하며 그 사실을 알려 주는 오류를
냅니다.

키와 사전 조건, 라우트 소스는 설정 레퍼런스의
[`type = "prefill_router"`](/ko/reference/configuration/#type--prefill_router)를 보세요.

### shunt로 넘어오는 것과 넘어오지 않는 것

스코어러는 같은 코드입니다. 그 주변은 전부 shunt의 것이므로, 위 표는 shunt 자신의
결과가 아니라 *접근 방식이* 값을 한다는 증거로 읽으세요.

| | 업스트림 벤치마크 | shunt |
| :-- | :-- | :-- |
| 스코어링 코어 | `switchyard-libsy` | 같은 크레이트, 같은 상수 |
| 신호 추출 | 업스트림의 프로바이더 중립 추출기 | shunt 자체 구현, Anthropic Messages 블록에서 |
| `tests_passed` / `repeated_failure` | 스코어러가 사용 가능 | 항상 `false` — 채워지지 않음 |
| `compacted` | 스코어러가 사용 가능 | `x-claude-code-context-compacted`에서 채워지고 세션 고정에 래치됨 |
| 모호한 턴의 판정자 | 선택적으로 사용 가능 | 없음. 피커 기본값으로 fall-open |
| 턴 간 티어 안정성 | 턴마다 독립 채점 | 비대칭 히스테리시스를 건 세션 고정 |
| 워크로드 | Terminal-Bench 2.1 태스크 | Claude Code 세션 |

이 중 둘은 반대 방향으로 작용합니다. shunt는 `tests_passed`와 `repeated_failure`를
채우지 않으므로 libsy의 반복 실패 승격이 빠집니다 — 벤치마크보다 엄격히 신호가 적습니다.
둘 다 이 추출기가 갖지 못한 근거, 곧 도구 결과의 *텍스트*를 요구합니다. 와이어 자체는 그
텍스트를 실어 나릅니다 — `tool_result` 블록에는 `content` 필드가 있습니다 — 하지만
추출기는 의도적으로 그것을 읽지 않습니다. 자유 서술형 결과 텍스트로 이 신호들을 판정한다는
것은 곧 내용 패턴 휴리스틱이고, 구조적 대리 지표는 테스트 실행만큼이나 `ls`에도 쉽게
발동하기 때문입니다. `compacted`는 이 무리에 속하지 않습니다. 트랜스크립트가 아니라 요청
헤더에서 오므로 libsy의 컴팩션 오버라이드는 여기서도 발동합니다
([스테이지 라우터](/ko/guides/stage-router/) 참고).
반대로 shunt의 히스테리시스는 벤치마크 하니스가 결코 치르지 않는 비용, 즉 Claude Code
세션에서 턴마다 티어를 뒤집는 대가가 비싸기 때문에 존재합니다([아래](#shunt가-더하는-것) 참고).

## 라우팅 알고리즘

### 1. 신호

shunt는 요청의 `messages` 배열을 두 번 훑습니다. 첫 번째는 어시스턴트 메시지를
`recent_turn_window`가 닿는 데까지만 뒤에서부터 훑으며 *최근*으로 칠 `tool_use` id를
모읍니다. 두 번째는 두 역할을 한 번에 앞에서부터 훑으며 `tool_use.id →
tool_use.name`을 만들고, 모든 `tool_result`를 그것이 답한 `tool_use_id`에 기록합니다.
이름은 훑는 도중이 아니라 훑고 난 뒤에 해석하므로, 자기 호출보다 앞서 나온 결과도
그대로 이어집니다. `tool_result` 블록은 도구 이름을 담지 않으므로, 이 조인이 추출기
전체가 딛고 선 단 하나의 지점입니다.

조인을 만드는 id를 빼면 읽는 필드는 `tool_use.name`과 `tool_result.is_error`
둘뿐입니다. 시스템 프롬프트도, 사용자 텍스트도, 도구 인자도 읽지 않습니다.

Claude Code는 실패를 등급 없는 불리언 하나로만 보고하므로, shunt가 직접 libsy의
`0.0 / 0.3 / 0.7 / 1.0` 심각도 척도에 매핑합니다.

| 조건 | `severity` |
| :-- | :-- |
| 윈도 안에 실패한 결과 없음 | `0.0` |
| 윈도 안에 실패한 결과 있음 | `0.7` (hard) |
| 윈도 안의 `Task` 실패 — 위임된 서브에이전트 실행 전체가 무너짐 | `1.0` (critical) |
| 마지막 두 완료 결과가 모두 실패하고 둘 다 윈도 안 — 회복 중이 아님 | `1.0` (critical) |

도구 이름은 [어휘](/ko/guides/stage-router/#도구-어휘)에 따라 `Observe`, `Mutate`,
`Plan`, 미분류로 나뉩니다. `Bash`는 의도적으로 미분류입니다 — `git status`,
`rm -rf`, `cargo test`를 가르는 것은 `input.command`를 읽는 것뿐이고, 그것이 바로 이
설계가 피하려는 취약한 추론입니다.

완료된 도구 호출이 하나도 없으면 추출은 아무것도 반환하지 않고 턴은 피커 기본값을
받습니다. 빈 대화는 "efficient"로 채점되지 않습니다.

### 2. 차원

신호는 두 축으로 투영됩니다 — 무언가 *잘못되었는가*, 그리고 에이전트가 *생산하고
있는가*.

| 차원 | 의미 | 미는 방향 |
| :-- | :-- | :-- |
| `severity` | 윈도 내 최대 오류 심각도, `[0, 1]` | Capable |
| `spinning` | 읽기·계획·쓰기·편집이 전무한 깊은 턴 — 순수한 헛돎 | Capable |
| `exploring` | 읽거나 계획하지만 쓰지도 편집하지도 않는 깊은 턴 | Capable |
| `production_intensity` | 최근 도구 연산 중 쓰기+편집의 비율 | Efficient |

`spinning`과 `exploring`은 둘 다 `turn_depth >= 8`을 요구합니다. 쓰기가 없는 초반
턴은 정체가 아니라 평범한 탐색입니다. 둘은 같은 "생산하지 않음" 상태를 조사 활동
유무로 분할하므로 최대 하나만 발동하고, 생산 축이 이중으로 계산되는 일은 없습니다.

### 3. 점수

최대치에 도달한 차원 하나가 `0.10`의 신호 단위 하나를 기여하며, `severity`는 hard
상한인 `0.7`로 정규화되어 같은 가중치에 놓입니다.

```
raw   = 0.10 × (severity / 0.7 + spinning + exploring − production_intensity)
score = tanh(5.0 × raw)          // 부호: + capable, − efficient
confidence = |score|
```

게인 `5.0`이 범위를 쓸 만하게 만듭니다. 이것이 없으면 신뢰도는 `±0.20` 부근에서
포화해 어떤 유의미한 문턱에도 닿지 못합니다.

설계는 **상호 보강적**입니다. 어떤 단일 축도 혼자서 판정을 확정할 수 없습니다.

| 합치하는 신호 | `raw` | `confidence` | `0.5` 기본값 통과? |
| :-- | --: | --: | :-- |
| 하나 포화 | `0.10` | `tanh(0.5) ≈ 0.46` | 아니오 |
| 둘이 상호 보강 | `0.20` | `tanh(1.0) ≈ 0.76` | 예 |

`0.5` 기본값은 여기서 나옵니다. 잘못된 신호 하나만으로는 턴을 움직이기에 부족하고,
합치하는 신호 둘이면 충분합니다.

### 4. 판정

`pick_tier`는 규칙 셋을 순서대로 돌리고, 먼저 발동한 것이 이깁니다.

1. **하드 승격** → capable. 심각도 critical, 컴팩션된 컨텍스트, 또는 최근 창에서
   같은 실패가 반복된 경우. 스코어러를 건너뛰고 `confidence: 1.0`을 보고합니다.
2. **스코어러.** 중앙값 주변의 모호한 구간 밖이면 부호를 따릅니다.
3. **Fall-open.** 구간 안이면 libsy가 `ConsultClassifier`를 반환합니다. shunt는
   분류기를 돌리지 않으므로 턴은 피커의 기본 티어에 안착합니다.

예전에는 네 번째 규칙이 있었습니다. 테스트가 통과한 정착된 턴을 하드 *강등*하는
규칙인데, 업스트림이 제거했습니다. 이제 테스트 통과는 libsy 자체의 capable hold를
해제할 뿐이고, shunt는 그 hold를 쓰지 않습니다.

규칙 1의 세 가지 방아쇠 중 오늘의 shunt에서 발동하는 것은 둘입니다. critical 심각도는 위
심각도 표의 두 경로를 통해 발동하고, 컴팩션된 컨텍스트는 트랜스크립트가 아니라 요청 헤더인
`x-claude-code-context-compacted`에서 옵니다 — 그래서 도구 활동이 전혀 없는 턴에서도 이
방아쇠가 발동할 수 있습니다. 반복 실패 절반은 libsy가 *같은 실패*인지를 결과 텍스트와 자체
오류 표를 대조해 판정하는데 Claude Code가 보내는 `is_error` 불리언으로는 그것을
뒷받침할 수 없어서 잠들어 있습니다. shunt 자체의 "마지막 완료 결과 둘이 모두 실패"
규칙은 `severity`를 거쳐 이미 규칙 1에 도달합니다.

### 5. 히스테리시스

여기까지는 한 턴을 고립적으로 판정합니다. 그다음 shunt는 그 판정이 세션의 고정된
티어를 움직이도록 허용하기 전에 자체 게이트를 겁니다.

| 방향 | 요구 조건 |
| :-- | :-- |
| Efficient → Capable | 스코어러가 실제로 내린 판정이 `confidence_threshold`(0.5) 통과 |
| Capable → Efficient | 스코어러가 실제로 내린 판정, **그리고** `min_dwell_turns` 경과, **그리고** `deescalate_threshold`(0.75) |

Fall-open, 모호한 턴, 도구 활동이 없는 턴은 증거가 아니라 피커의 기본값이며, 어느
방향으로도 핀을 움직일 수 없습니다.

신뢰도 게이트에는 면제가 없습니다. 예전에는 `tests_passed` 지름길을 위한 면제가
있었습니다. 그 지름길은 신뢰도를 아예 보고하지 않았기 때문입니다. 업스트림에서 그
규칙이 사라지면서, 이제 증거로 인정되는 모든 출처가 신뢰도를 보고하고, 신뢰도를
보고하지 않는 턴은 신뢰하는 대신 붙잡아 둡니다. 그 자리를 대신한 libsy의
`capable_hold` — 앞선 승격이 아직 유지되고 있다는 뜻 — 도 증거가 아닙니다. 위 표의
`sticky` 행과 같은 개념이고, 그것을 찍는 것은 libsy의 상태 있는 분류기뿐인데 shunt는
그것을 호출하지 않습니다.

## shunt가 더하는 것

Switchyard는 프로바이더 중립이라 티어 전환의 대가를 가격 매길 필요가 없습니다.
shunt는 Claude Code 게이트웨이이므로 그래야 하고, 여기 나열된 것 대부분이 그 차이에서
나옵니다.

### Claude Code의 실제 도구 어휘

스코어러가 알고 싶은 것은 어떤 호출이 관찰했는지, 변경했는지, 계획했는지입니다.
프로바이더 중립 라우터는 그것을 추론해야 하지만 shunt는 이름을 압니다. 직접 매칭하는
이름은 열네 개입니다. 관찰은 `Read`, `Glob`, `Grep`, `NotebookRead`, `WebFetch`,
`WebSearch`, `BashOutput`, 변경은 `Edit`, `NotebookEdit`, `Write`, 계획은
`TodoWrite`, `Task`, `EnterPlanMode`, `ExitPlanMode`입니다. 그중 하나는 범주 이상의
대우를 받습니다. *실패한* `Task`는 명령 하나가 아니라 위임된 서브에이전트 실행 전체가
무너진 것이므로 hard가 아니라 critical로 채점됩니다.

### 전환이 공짜가 아니기에, 비대칭 히스테리시스

긴 Claude Code 세션에서 티어 전환은 구체적으로 세 가지를 치릅니다.

- **프롬프트 캐싱은 모델별로 키가 걸립니다** — 전환하면 따뜻한 프리픽스를 잃고 새
  티어에서 캐시 쓰기를 전액 지불합니다.
- **Codex 컨티뉴에이션**은 모델을 시그니처에 해싱하므로, 전환은 전체 재전송을
  강제하고 shunt가 방금 벌어놓은 업로드 절감을 되돌려줍니다.
- **프로바이더를 넘는 전환**은 세션의 풀링된 커넥션과 끈적한 계정 슬롯까지
  버립니다.

턴마다 독립적으로 채점하면 긴 세션은 라우팅하지 않을 때보다 *더* 비쌀 수 있습니다.
두 방향이 불평등한 이유이자, 히스테리시스가 shunt 통합의 곁가지가 아니라 핵심인
이유입니다.

### 세션 id를 흘리지 않는 세션 고정

판정은 `(광고된 모델 id, 세션 id, agent id)` 단위로 고정되며 각 id의 키는 SHA-256
프리픽스입니다 — 둘 다 해싱되고 저장되지 않습니다. agent id는 Claude Code가 모든 위임
턴에 보내는 `x-claude-code-agent-id`이므로, `Task` 자식은 자신을 띄운 부모와 분리되어
고정됩니다. 자식의 실패가 부모를 승격시키지 않고, 자식의 턴이 부모의 dwell을 진행시키지도
않습니다. 저장소는 부모 세션 4096개와 그와 별개인 자식 고정 4096개에서 각각 상한에 걸리고,
삽입 경로에서 축출하며 백그라운드 태스크가 없고, 아무것도 영속하지 않습니다. 정리는 자신이
늘어난 범위에만 닿으므로, 넓은 팬아웃이 그것을 기다리는 부모를 축출할 수 없습니다.

고정은 컴팩션 래치도 함께 실어 나릅니다. `x-claude-code-context-compacted`를 보낸 턴은
compacted로 채점되고 그 플래그가 저장되므로 — 헤더는 컴팩션당 한 번만 옵니다 — 뒤따르는
턴들도 고정이 만료되거나 리로드가 버릴 때까지 같은 방식으로 채점됩니다.

핀은 자신이 만들어진 라우터 테이블의 지문도 기억하므로, 핫 리로드를 가로질러 라우터
하나를 편집하면 그 라우터의 핀만 버려집니다. 그 지문은 설정 구조체를 점 접근이 아니라
구조 분해로 읽으므로, 나중에 키가 추가되면 낡은 핀이 조용히 살아남는 대신 컴파일이
깨집니다.

### 위임된 작업은 다른 타깃으로 갈 수 있다

Switchyard의 `subagents` 오버레이는 `[models.subagents]`로 넘어오며, 라우터 테이블 안이
아니라 항목 위에 놓입니다 — 고정 항목에는 라우터 테이블이 없고, 업스트림의 "subagents를
곁들인 passthrough"가 여기서는 바로 그 고정 항목이기 때문입니다. 그 id를 요청하는 `Task`
자식이나 훅 에이전트, 워크플로 서브에이전트는 오버레이의 `target`으로, 또는 자신의
`x-claude-code-agent-type`과 맞는 `by_type` 항목으로 우회됩니다. 부모 자신의 턴은 이
테이블을 전혀 보지 않습니다.

```toml
[models.subagents]
type = "passthrough"
target = "claude-haiku-4-5"
by_type = { Explore = "claude-haiku-4-5", fork = "claude-sonnet-4-6" }
```

shunt가 더하는 것은 "위임"을 읽어내는 방식입니다. 업스트림은 자기 `claude_lineage` 헤더
하나에만 기대지만, shunt는 `x-claude-code-request-class`를 먼저 읽고(`subagent`와
`workflow`는 위임이고, `main`은 에이전트 id가 함께 실려 와도 위임이 아니며, `compaction`과
`auxiliary`는 오버레이를 절대 타지 않는 하네스 유지보수입니다) 그 클래스가 전송되지 않을
때만 에이전트 id로 폴백합니다 — 기본 게이트웨이 배포에서는 실제로 전송되지 않습니다.
`by_type` 키는 헤더의 값 그대로이고 대소문자까지 그대로이며, 프로젝트 에이전트는 자기
이름이 감춰진 채 `custom`으로 도착합니다. 이 오버레이는 상태를 갖지 않습니다. 우회된
자식은 채점되지도, 고정되지도, 부모의 dwell을 진행시키지도 않으며, 그 턴은
`x-gateway-route-source`에 `subagent_type` 또는 `subagent`를 보고합니다.

### 핫 패스에 LLM 판정자를 두지 않는다

신호가 불확실하면 libsy는 `PickOutcome::ConsultClassifier { default_tier }`를
반환합니다. 기본값에서 shunt는 그것을 답으로 취급하고 `default_tier`를 씁니다. 그래서
핫 패스에는 판정자가 없습니다 — 두 번째 모델 호출도, 두 번째 자격 증명도, 라우터가 가장
불확실한 바로 그 턴에서 늘어나는 지연도 없습니다. fall-open하는 것은 API와 싸우는 게
아니라, API가 문서화한 fall-open 경로 *그 자체* 입니다.

항목 단위로 다시 켤 수는 있습니다. `stage_router`에
[`[models.router.classifier]`](/ko/guides/stage-router/#판정-모델-폴백)를 두면 됩니다.
그러면 바로 그 턴들에서 판정자가 회복해주는 정확도를 되찾습니다 — 업스트림의 분류기
보조 구성이 측정한 것의 실질적인 일부입니다 — 대신 지연 시간과 판정 타깃 자신의 풀
쿼터를 치릅니다. 판정자는 결론이 나지 않은 턴에서만, 그리고 요청이 통과된 뒤에만
호출되며 `count_tokens` 탐침에는 호출되지 않습니다. 비용이 가장 불확실했던 턴에만
얹히고 다른 곳에는 얹히지 않는다는 뜻입니다. 판정 실패는 모두 `default_tier`로
돌아옵니다.

### 라우팅된 타깃은 평범한 모델 id

라우터의 출력은 공개 모델 id이므로 shunt의 일반 라우팅 사다리에 다시 진입해
페일오버 체인, 계정 풀, 어댑터 선택, `effort`, `service_tier`를 공짜로 물려받고,
추가 코드 없이 `/v1/models` 디스커버리에 나타납니다. 타깃이 또 라우터이면 시작
오류이므로, 해석은 깊이 카운터가 아니라 **구조적으로** 한 홉입니다.

### 클라이언트는 여전히 자신이 요청한 id를 본다

티어는 `upstream_model`을 타고 업스트림으로만 갑니다. 응답은 요청된 id를 보고하므로
Claude Code의 `/model` 표시와 `--resume` 모델 복원이 그대로 동작합니다.

### 요청하지 않으면 비활성

`[models.router]` 테이블이 없으면 라우터 분기는 기존 배포에 존재하지 않는 설정
필드에 대한 `Option` 검사 하나입니다. 라우팅 경로에서 달라지는 것은 없으며, 라우터를 쓴
항목들이 어떤 `type`을 선언했든 이 검사 비용은 같습니다.

## 통합 비용

의존성을 처음 채택할 때 `0.2.0`을 상대로 추정이 아니라 실측한 값입니다.

| | |
| :-- | :-- |
| 릴리스 바이너리 | **+115,376 바이트 (+0.31%)** |
| `Cargo.lock` 패키지 | **+33** (412 → 445) |
| 그중 미사용 | 약 26개. shunt가 호출하지 않는 분류기 경로를 위한 `jsonschema` 트리 |
| 실제 링크 여부 | `jsonschema` 트리는 링크되지 **않음** — 빌드된 바이너리에 `jsonschema` 문자열 0건, `num-bigint` 심볼 0건 |
| 포팅 대안 | 137줄 |

결정을 내린 것은 바이너리 결과였습니다. 링커가 분류기 트리를 통째로 떨어뜨리므로
크레이트에 의존하는 비용은 0.3% 남짓입니다. 137줄 포팅은 핀이 낡을 경우의 출구로
문서에 남아 있습니다.

그 릴리스에서 `main` 핀으로 옮기면서 추가된 패키지는 **하나도 없습니다** — 락은 445에
그대로입니다. 거기서 libsy가 새로 직접 의존하는 `http`, `regex`, `uuid`가 이미 shunt
트리에 있었기 때문입니다. 링크 여부 결과도 새 핀에서 그대로입니다. 릴리스 바이너리에
`jsonschema` 문자열 0건, `num-bigint` 심볼 0건입니다.

판정 경계를 위해 `switchyard-translation`을 가져오면서 락 항목이 셋 늘었습니다. 크레이트
자체와 `async-stream`, `async-stream-impl`입니다. `switchyard-protocol`은 libsy의 의존성
으로 이미 트리에 있었습니다.
