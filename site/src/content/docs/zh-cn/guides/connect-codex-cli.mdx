---
title: 连接 Codex CLI
description: 把 OpenAI Codex CLI 指向 shunt,让它在 ChatGPT/Codex OAuth 账户池上做负载均衡。
---

其他所有连接指南都是把 **Claude Code** 路由到某个后端。这一篇的方向正好相反:把 OpenAI 的
**Codex CLI** 指向 shunt,让 shunt 在一个 ChatGPT/Codex OAuth 账户池上为它做负载均衡。shunt 会
**逐字**中继 Codex CLI 的 OpenAI Responses 流量 —— 没有任何 Anthropic 转换 —— 因此该 CLI 与 shunt
之间说的,和它直连 `chatgpt.com` 时说的是同一套线上协议。

这是[入站 Codex 端点](/zh-cn/guides/inbound-codex-endpoint/)的实际用法;那一页是行为规范(故障转移表、
耗尽语义、重载规则),下面的步骤则是端到端的连接演练。这里引用的 Codex CLI 配置键来自 OpenAI 的
[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)与
[认证](https://learn.chatgpt.com/docs/auth)文档。

## 1. 在 shunt 上启用该端点

入站端点是**可选启用**的。添加该表并把它指向一个 `chatgpt_oauth` 提供方(默认的提供方名是
`codex`):

```toml
# shunt config.toml
[server.codex_endpoint]
provider = "codex"        # must be a chatgpt_oauth provider; "codex" is the built-in default
```

`codex` 是内置的 `chatgpt_oauth` 提供方,因此启用该端点不需要任何 `[providers.codex]` 块。若要指向
一个名字不同的提供方,请把它声明为 `[providers.<name>]` 表(见[配置参考](/zh-cn/reference/configuration/#providersname旧式)),
并在上面设置 `provider = "<name>"`。

```bash
shunt check                # validates the endpoint's provider exists + is chatgpt_oauth
shunt run
```

`[server.codex_endpoint]` 不存在时,这些路由一个都不会注册,shunt 默认的 HTTP 暴露面保持不变。存在
时,启动校验会**拒绝**未知的 `provider`,或其 `auth` 不是 `chatgpt_oauth` 的提供方 —— 该端点注入的是
运营者的 Codex bearer,因此只有 `chatgpt_oauth` 提供方符合条件。每个键见[配置参考](/zh-cn/reference/configuration/)。

## 2. 把 Codex CLI 指向 shunt

Codex CLI 会把 `/responses` 追加到它使用的任何 base URL 之后(Codex 说的是 OpenAI Responses 线上
协议 —— `wire_api = "responses"` 是它唯一支持的取值),因此 shunt 注册了三条路由,下面任何一种客户端
形态都会落到其中之一:

| Codex CLI `~/.codex/config.toml` | 命中的 shunt 路由 |
| :-- | :-- |
| 自定义提供方 `base_url = ".../v1"` | `POST /v1/responses` |
| `openai_base_url = ".../v1"` | `POST /v1/responses` |
| `chatgpt_base_url = ".../backend-api/codex"` | `POST /backend-api/codex/responses` |

**推荐 —— 自定义模型提供方**。配合 `requires_openai_auth = false`,从 CLI 的视角看它是免认证的,因此
**完全不需要本地的 `codex login`** —— 账户由 shunt 提供 —— 而且两种呈递 shunt token 的方式(步骤 3)
它都支持:

```toml
# ~/.codex/config.toml
model_provider = "shunt"          # select it as the active provider
model = "gpt-5.6-sol"             # an entitled slug — see step 5

[model_providers.shunt]
name = "shunt"
base_url = "http://127.0.0.1:3001/v1"
wire_api = "responses"            # the only supported value; also the default
requires_openai_auth = false      # shunt handles auth; the CLI needs no ChatGPT/API login here
```

**更简单 —— 覆盖一个 base URL**(不需要提供方块):

```toml
# ~/.codex/config.toml — pick one
openai_base_url  = "http://127.0.0.1:3001/v1"                 # + OPENAI_API_KEY = your shunt token
chatgpt_base_url = "http://127.0.0.1:3001/backend-api/codex"  # loopback only (ChatGPT login mode)
```

`openai_base_url` + `OPENAI_API_KEY=<shunt-token>` 是 LiteLLM/llmgateway 的惯用法 —— CLI 会把该
token 以 `Authorization: Bearer` 发送,shunt 接受这种方式(步骤 3),所以这种形态**即使配置了
`[server.auth]` 也能工作**。`chatgpt_base_url` 会让 CLI 停留在 ChatGPT 登录模式并发送它*自己的*
ChatGPT token,而 shunt 无法把它当作客户端 token 接受 —— 因此**只应在未设门控的(回环)shunt 上**使用。
这两种方式都让 CLI 运行在它自己的 OpenAI/ChatGPT 认证模式下,因此都需要本地的 `codex login`;上面的
自定义提供方连这一步都省了。



<Aside type="caution" title="在 config.toml 中设置 base URL,而不是通过 OPENAI_BASE_URL 环境变量">

请把 `openai_base_url` 写进 `~/.codex/config.toml`(用户级)。`OPENAI_BASE_URL`
**环境变量**无法重定向 Codex CLI 的 Responses **WebSocket** 传输 —— CLI 会继续打开
`wss://api.openai.com/v1/responses`,完全绕开 shunt,并因为把你的 shunt token 直接呈递给 OpenAI 而以
`Incorrect API key` 失败。只有配置键才会同时重定向 HTTP 与 WebSocket 两条路径。(`chatgpt_base_url`、
`model_provider` 和 `experimental_realtime_ws_base_url` 同理:它们都是用户级 `~/.codex/config.toml`
的键 —— CLI 会忽略项目本地 `.codex/config.toml` 中的它们,而且没有等效的环境变量。)使用
`openai_base_url` 时,CLI 会先*尝试* WebSocket,shunt 会在同一个 Responses 路径上接受这次升级。
上面的自定义 `model_provider` 的 `supports_websockets` 默认关闭,所以它直接走 HTTP。

</Aside>



CLI 自己本地的 `~/.codex/auth.json` 登录**与哪个账户来应答无关** —— 每个请求都从 shunt 的池中取用一个
账户。回环的 `base_url` 可以保持纯 `http://`;远程场景请使用 `https://`。在 shunt 提供方上设置
`supports_websockets = true` 是可选的 —— 这个端点同时支持 HTTP/SSE 与 WebSocket(见下文)。



<Aside type="tip" title="用 profile 隔离它">

把 shunt 的配置块放进 profile 文件 `~/.codex/shunt.config.toml` 并运行 `codex --profile shunt`,就能让
你原有的 Codex 配置保持不变。profile 文件使用相同的顶层键,并且只需要写下与基础配置不同的值。

</Aside>



## 3. 提供 shunt 客户端 token(当配置了 `[server.auth]` 时)

如果 shunt 配置了 [`[server.auth]`](/zh-cn/guides/shared-gateway/) —— 回环之外的场景都推荐配置 ——
请用**两种**方式之一提供 shunt 客户端 token;shunt 两种都接受。

**A. 作为 OpenAI 风格的 Bearer key** —— LiteLLM/llmgateway 的惯用法。把 shunt token 设为 API key,CLI
会以 `Authorization: Bearer <shunt-token>` 发送它:

```toml
# ~/.codex/config.toml — built-in openai provider (no provider block needed).
# Set the base URL here, NOT via the OPENAI_BASE_URL env var (see the caution in step 2).
openai_base_url = "http://127.0.0.1:3001/v1"
```

```bash
# then present only the token via env — the CLI sends it as Authorization: Bearer
export OPENAI_API_KEY="<shunt-token>"
```

```toml
# or a custom provider — env_key becomes the Bearer
[model_providers.shunt]
base_url = "http://127.0.0.1:3001/v1"
wire_api = "responses"
env_key = "SHUNT_TOKEN"      # reads $SHUNT_TOKEN, sent as Authorization: Bearer
```

**B. 作为 `x-shunt-token` 头部**(或 `[server.auth].header` 所指定的任何名字)。只有自定义提供方才能附加
头部;用 `env_http_headers` 把密钥留在 `config.toml` 之外:

```toml
[model_providers.shunt]
name = "shunt"
base_url = "http://127.0.0.1:3001/v1"
wire_api = "responses"
requires_openai_auth = false
env_http_headers = { "x-shunt-token" = "SHUNT_TOKEN" }   # reads $SHUNT_TOKEN
```

```bash
export SHUNT_TOKEN="<token>"
```

(或者硬编码 `http_headers = { "x-shunt-token" = "<token>" }`。)无论哪种方式,该 token 都会与
`[server.auth]` 的列表比对;缺失或错误的 token 返回 `401 authentication_error`。完全不配置
`[server.auth]` 时,该端点对任何能触达它的人开放 —— 回环场景没问题,共享网关则不行。客户端的
bearer/头部**仅**用于向 shunt 认证 —— 它会被剥除,绝不会转发给 Codex 后端。



<Aside type="note" title="你的凭据不会到达后端 —— 但你的身份头部会">

你所提供的 `Authorization: Bearer` / `x-shunt-token` **仅**用于向 shunt 认证(步骤 3),之后即被
**剥除** —— 它和任何客户端凭据都不会转发到上游。shunt 只换入池中账户的 `Authorization` bearer 与
`chatgpt-account-id`。CLI 发送的其他一切都会被**逐字**转发,因此你的 CLI **自己的** `version` 会到达
后端(而不是 shunt 固定的某个值),`minimal_client_version` 的模型门控(步骤 5)表现也与直连
`chatgpt.com` 时完全一致。

</Aside>



## 4. 在 shunt 上预配账户池

该端点原封不动地复用 [Codex 多账户](/zh-cn/guides/codex-multi-account/#配置账户池)的账户池 —— 请在
**shunt** 所在主机上预配账户,而不是 CLI 那一侧:

```bash
codex login                       # sign in to a ChatGPT account (browser flow)
shunt login codex --name main     # capture it into shunt's store
# Each additional pool account needs its own login + capture (a separate ChatGPT
# account): `codex login` then `shunt login codex --name backup`, and so on.
```

```toml
# shunt config.toml
[[providers.codex.accounts]]
name = "main"

[[providers.codex.accounts]]
name = "backup"     # each declared name must be provisioned above; an unprovisioned
                    # account is skipped on failover (its credential fails to resolve)
```

选择是**会话粘性**的:Codex CLI 自己的 `session-id` 请求头部决定账户的 key,因此一段对话只要账户保持
健康就一直留在同一个账户上,随后才会故障转移(429 → 轮换,401 → 刷新并重试,5xx → 冷却并轮换)。
此端点上成功的池化响应会带 `x-shunt-account: <name>` 头部 —— 流式响应也不例外,因为入站透传只在获胜上游响应之后才提交(出站 Responses 池的早期提交 HTTP 流式响应则改用 `event: account` 帧标注账户,见 Codex 多账户指南)。在启用了 [`[server.auth]`](/zh-cn/reference/configuration/)
的共享网关上,粘性 key 按已认证的客户端隔离,因此恰好发送相同 `session-id` 的不同客户端会使用不同的
粘性 key —— 从而避免跨客户端的粘性 key 碰撞。(这些 key 是不同的;两个不同的 key 仍可能哈希到同一个
账户。)

在**没有**配置 `[[providers.codex.accounts]]` 且存储为空时,该端点会回退到单个默认的
`~/.codex/auth.json` 凭据 —— 没有池,也没有故障转移 —— 因此只要设置了 `[server.codex_endpoint]`,一个
Codex 登录就能立刻工作。



<Aside type="note" title="无头环境下的预配">

`shunt login codex` 捕获的是**基于文件**的 `~/.codex/auth.json`,因此在 shunt 主机上请保持
`cli_auth_credentials_store = "file"`(默认值),而不是 `keyring`。在没有浏览器的服务器上,请用 Codex
的设备码流程(`codex login --device-auth`)登录该账户,或者在笔记本上完成 `codex login` 再把
`~/.codex/auth.json` 复制到 shunt 主机 —— 参见
[在无头设备上登录](https://learn.chatgpt.com/docs/auth#login-on-headless-devices)。

</Aside>



## 5. 选择一个有权限的模型



<Aside type="caution" title="带 codex 后缀的 slug 会被拒绝">

入站请求体中的 `model` 会被**逐字**转发到上游,而 ChatGPT 账户后端只接受你的账户**当前有权限**使用的
slug —— 它会以 `400` **拒绝** `gpt-*-codex` 这类 slug(例如 `gpt-5.2-codex`)。如果你的 Codex CLI 默认
使用某个 `-codex` 模型,请把它覆盖为一个有权限的 slug,例如写在 `~/.codex/config.toml` 中:

```toml
model = "gpt-5.6-sol"   # entitled slug, not a *-codex one
```

当前有权限的 slug 是 `gpt-6-astra` / `-sol` / `-luna`、`gpt-5.6-sol` / `-terra` / `-luna` 以及
`gpt-5.5` / `gpt-5.4` —— 较早的账户可能只有靠前的那些。权威列表见
[ChatGPT / Codex → 将一个模型路由到 `codex`](/zh-cn/guides/codex/#3-将一个模型路由到-codex)。请求一个你的
订阅所不具备的模型时,失败方式与直连 `chatgpt.com` 完全一致。

</Aside>



## 6. 验证

针对这三条路由中的任意一条发起一个原始 Responses 请求,应当被逐字中继;当一个池化账户获胜时,响应
会带一个指明该账户的 `x-shunt-account` 头部 —— 入站透传只在获胜上游响应之后才提交,因此该头部指明的
是实际处理该请求的账户:

```bash
curl -N -i -X POST http://127.0.0.1:3001/v1/responses \
  -H "content-type: application/json" \
  -H "x-shunt-token: <token>" \
  -d '{"model":"gpt-5.6-sol","input":"say hi","stream":true}'
```

- 返回 `200`,带 `content-type: text/event-stream` 和标注池账户名的 `x-shunt-account:` 头部 ⇒ 池已服务
  该请求,且 SSE 被原样中继。
- 返回 `401 authentication_error` ⇒ `x-shunt-token` 缺失或无效(步骤 3)。
- 返回指明模型的 `400` ⇒ 该账户对这个 slug 没有权限(步骤 5)。

然后用真正的 Codex CLI 跑一轮 —— 除了 base URL 之外,CLI 侧不需要任何代码改动就能经由账户池往返。关于
这条路径与 `/v1/messages` 路径的差异,见[入站 Codex 端点](/zh-cn/guides/inbound-codex-endpoint/);已注册的
路由见 [HTTP 端点](/zh-cn/reference/endpoints/)。

## 7. 通过身份提供商登录(gateway OAuth)

第 3 步的共享 token 让所有开发者共用同一个身份。如果你的组织运行着身份提供商(IdP),Codex CLI 原生的 `gateway_oauth` 会让每位开发者通过 IdP 登录,而 shunt 只**验证**返回的访问令牌:它不签发令牌,也不保存会话。Codex 保留 `Authorization`,所以把令牌放在 cookie 或自定义头部中传递,再由两个可选的 `[server.auth]` 键告诉 shunt 读取哪一个。Codex 一侧的说明见 OpenAI 的 [Connect to a gateway](https://learn.chatgpt.com/docs/enterprise/connect-to-a-gateway?gateway-auth=oauth) 指南。

在 Codex 一侧,给 shunt 提供商添加 `gateway_oauth`,并保持 `requires_openai_auth = false`:

```toml
# ~/.codex/config.toml
model_provider = "shunt"

[model_providers.shunt]
name = "shunt"
base_url = "https://shunt.example.com/v1"
wire_api = "responses"
requires_openai_auth = false

[model_providers.shunt.gateway_oauth]
authorization_url = "https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/authorize"
token_url = "https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token"
client_id = "<codex public client id>"
scopes = ["api://<shunt-app-id>/.default"]
# resource = "..."                                  # 可选,IdP 需要时再设置
delivery = { kind = "cookie", name = "auth-openid" }
# 或:delivery = { kind = "header", name = "X-Gateway-Token", scheme = "Bearer" }
redirect_port = 8765                                # 固定的 loopback 端口,见下文
```

在 shunt 一侧,指定同一个 cookie 或头部名称,并描述 issuer:

```toml
# shunt config.toml
[server.auth]
jwt_cookie = "auth-openid"          # kind = "cookie" 时必须等于 delivery.name
# jwt_header = "X-Gateway-Token"    # kind = "header" 时必须等于 delivery.name

[[server.auth.jwt]]
issuer = "https://login.microsoftonline.com/<tenant-id>/v2.0"
audience = ["api://<shunt-app-id>"]
authorized_parties = ["<codex public client id>"]
require = { tid = "<tenant-id>" }
identity_claim = "preferred_username"     # 或不可变的 "oid"
max_token_age_seconds = 5400
```

根据 `delivery` 的类型设置这两个键之一。两者都是可选的,并支持 hot-reload。验证后的 `identity_claim` 与 bearer JWT 一样,成为日志、用量、支出限制和 sticky key 中的调用者身份。全部校验规则见[配置参考](/zh-cn/reference/configuration/)。

### Microsoft Entra ID 的注意事项

上面示例中的每个值都对应下列某一项:

- **访问令牌必须是 JWT。** shunt 在本地验证,不做 introspection。请求你为 shunt 注册的 API 作用域(`scopes` 中的 `api://<shunt-app-id>/.default`),Entra 就会签发 JWT。Google OAuth 这类 opaque 访问令牌无法使用。
- **使用 v2 令牌。** 把 API 应用注册的 `accessTokenAcceptedVersion` 设为 `2`。v2 令牌的 issuer 是 `https://login.microsoftonline.com/<tenant-id>/v2.0`。v1 令牌的 issuer 是 `https://sts.windows.net/<tenant-id>/`,并使用 `appid` 而不是 `azp`,与上面的条目不匹配。
- **与令牌的 `aud` 一致。** `audience` 填 `api://<shunt-app-id>` 或应用 ID 的 GUID,以令牌实际携带的为准。
- **把 Codex 客户端列入 `authorized_parties`。** v2 令牌的 `azp` 是请求令牌的客户端(这里是 Codex public client),而 `authorized_parties` 默认等于 `audience`。不显式写出客户端 ID,所有令牌都会被拒绝。
- **不要使用 `email_domains`。** Entra 访问令牌没有 `email_verified`,也常常没有 `email`,所以邮箱规则会拒绝所有令牌。用 `require = { tid = "<tenant-id>" }` 按租户授权,身份取自 `preferred_username` 或 `oid`。
- **调高 `max_token_age_seconds`。** 访问令牌的默认有效期在 60 到 90 分钟之间随机,可能超过默认值 `3600`。请设为约 `5400`。参见 Microsoft 文档中的[访问令牌](https://learn.microsoft.com/en-us/entra/identity-platform/access-tokens)和[令牌有效期](https://learn.microsoft.com/en-us/entra/identity-platform/configurable-token-lifetimes)。
- **注册固定的重定向 URI。** 在 **public client** 上注册 `http://127.0.0.1:<redirect_port>/callback`,并在 Codex 配置中设置相同的 `redirect_port`。

### 需要了解的行为

- **浏览器与 loopback 回调。** 原生 gateway OAuth 会打开浏览器并监听 loopback 端口,没有 device-code 回退。通过 SSH 连接时,设置 `redirect_port` 并用 `ssh -L <port>:127.0.0.1:<port>` 转发。
- **槽位顺序。** shunt 依次尝试静态 token、`Authorization: Bearer` JWT、`jwt_header`、`jwt_cookie`,第一个验证成功的生效。因此 `Authorization` 中的 ChatGPT bearer 会落到 cookie 上。只有[入站 Codex 端点](/zh-cn/guides/inbound-codex-endpoint/)读取这些新槽位;`/v1/messages`、`/v1/models`、`/usage` 和 Codex discovery 路径对 JWT 仍只接受 bearer。
- **Origin 规则。** 仅当请求没有 `Origin`,或 `Origin` 与其 `Host` 匹配时才使用 cookie,所以网站无法借浏览器持有的 cookie 发起已认证的轮次。Codex CLI 不是浏览器,不发送 `Origin`。出于同样的原因,不要让 `jwt_cookie` 指向浏览器为网关域名持有的 cookie(例如 SSO 代理的 `CF_Authorization`)。头部槽位没有这条规则。
- **WebSocket 过期。** 握手时的凭据在每一轮都会重新验证。连接期间 IdP 令牌过期,下一轮会以 `401` 错误帧失败,Codex 随后用刷新后的令牌重新连接。
- **不会转发。** 配置的头部和所有 `cookie` 头部在发往上游之前都会被移除。
- **大小限制。** Entra 访问令牌可能有几 KB。若设置了 `[server.limits] max_request_header_bytes`,它会计入该上限;反向代理通常把 cookie 限制在约 4 KB。任何一项成为问题时,用 `delivery = { kind = "header", ... }` 代替 cookie。
- **模型元数据。** 仅有 OAuth 不会启用远程模型目录 discovery。自定义模型元数据请使用 `model_catalog_json`。

## HTTP/SSE 与 WebSocket

这个端点在同样的三个 Responses 路径上同时接受 HTTP `POST` 请求和 WebSocket `GET` 升级,因此 Codex CLI
的 shunt 提供方上的 `supports_websockets` 既可以保持关闭(其默认值,只走 HTTP),也可以设为 `true`。
两种传输都不依赖目标提供方的 `websocket = true`,那个设置控制的是 shunt 自己的出站传输。套接字的行为见
[WebSocket 传输](/zh-cn/guides/inbound-codex-endpoint/#websocket-传输)。
