---
title: Stage Router
description: Let one model id pick between a capable and an efficient tier per turn, from the conversation's recent tool-result history rather than its prompt text.
---

A `[[models]]` entry normally names one destination. A **stage router** names two
— a capable tier and an efficient one — and lets the conversation decide which
serves each turn. Errors, stalled investigation, and exploratory reading route
up; routine production once the plan is settled stays down.

This is opt-in and inert by default. Configure no `[models.stage_router]` table
and shunt routes exactly as it did before: by the request's `model` id, and
nothing else.

## What it reads

Only **structured protocol metadata** from the request body:

- `tool_use.name` — which tool the assistant called
- `tool_result.is_error` — whether the result came back as a failure

Both are load-bearing fields of the Anthropic Messages wire format. The router
never reads the system prompt, the user's text, or a tool's arguments, so it does
not inherit the failure mode of proxies that fingerprint prompt shape and break
on the next Claude Code release.

A `tool_result` block does **not** carry the tool's name. The only link is
`tool_use_id` → `tool_use.id`, and that join is the single point the whole
extractor stands on.

### The vocabulary

shunt knows Claude Code's actual tool names, which is where it can do better than
a provider-neutral router:

| Category | Tools |
| :-- | :-- |
| Observe | `Read`, `Glob`, `Grep`, `NotebookRead`, `WebFetch`, `WebSearch`, `BashOutput` |
| Mutate | `Edit`, `NotebookEdit`, `Write` |
| Plan | `TodoWrite`, `Task`, `EnterPlanMode`, `ExitPlanMode` |
| Uncategorised | everything else, including `Bash`, `Skill`, `KillShell`, and every `mcp__*` tool |

Every `Plan` call — `ExitPlanMode` included — counts as planning activity, which
reads as exploration and pushes **up**, not down. One name gets more than its
category: a failed `Task` is scored critical rather than merely hard, because it
is a whole delegated subagent run collapsing rather than one command failing. Two
consecutive failures at the end of the conversation are critical too — a session
that is not recovering.

`Bash` is deliberately uncategorised. `git status` observes, `rm -rf` mutates,
and `cargo test` is a settled-state signal — only `input.command` separates them,
and classifying command strings would be exactly the kind of fragile inference
this design avoids.

## How it decides

Signals are scored by [`switchyard-libsy`][libsy], the scorer from
[NVIDIA-NeMo/Switchyard][sy], which is the calibrated part and is not
reimplemented here. One saturated signal alone scores about `0.46` and cannot
decide a turn; two corroborating signals reach about `0.76`.

When the signals are inconclusive the scorer asks for an LLM judge. **shunt runs
none** — it falls open to the picker's default instead, which keeps the hot path
free of an extra model call and an extra credential.

The full scoring formula, the published benchmark results behind it, and what
shunt adds on top are in [Switchyard Integration](/guides/switchyard/).

[libsy]: https://github.com/NVIDIA-NeMo/Switchyard/tree/3ddea9d30174ad835cf505a93617ba251c8eb8dd/crates/libsy
[sy]: https://github.com/NVIDIA-NeMo/Switchyard

## Why going down is harder than going up

A tier flip is not free, and on a long Claude Code session the cost is concrete:

- **Prompt caching is keyed per model.** A flip forfeits the warm prefix and pays
  a full cache write on the new tier.
- **Codex continuation** hashes the model into its signature, so a flip forces a
  full-input re-send and gives back the upload trimming shunt just earned.
- **A cross-provider flip** also abandons the session's pooled connection and its
  sticky account slot.

So the two directions are deliberately unequal:

| Direction | Requires |
| :-- | :-- |
| Efficient → Capable | `confidence_threshold` (0.5) alone. A turn the cheap tier cannot serve costs more than the forfeited cache prefix. |
| Capable → Efficient | `min_dwell_turns` **and** `deescalate_threshold` (0.75) **and** a decision the scorer actually made. |

A fall-open or a turn with no tool activity is the picker's default, not
evidence, and cannot move a tier in either direction.

## Session pinning

Decisions are pinned per `(model id, session id, agent id)`, read from
`x-claude-code-session-id` and `x-claude-code-agent-id`. Both ids are hashed and
never stored. Two router-backed models used in the same session keep independent
tiers.

**A sub-agent keeps a pin of its own.** A `Task` child sends its parent's
session id with an agent id of its own, so it reads and writes a separate entry:
its failures no longer escalate the parent, and its turns no longer count toward
the parent's dwell. Claude Code sends that header on every delegated turn
without any opt-in, so this holds on a default shunt deployment with no client
change. Child pins are evicted against a budget of their own — 4096, beside the
4096 parent sessions — and a trim only ever reaches the scope it grew, so a wide
fan-out cannot evict the parent that is waiting on it.

**A compaction escalates, and the escalation holds.** Claude Code marks the
first turn after a context compaction with `x-claude-code-context-compacted`,
once. shunt scores that turn as compacted, which reaches the scorer's hard
override and routes to the capable tier even when the post-compaction history
has no tool activity to read, and latches the flag onto the session's pin so the
turns after it resolve the same way. This header only reaches shunt when the
client sets `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` (see
[Client Environment Variables](/reference/client-environment/)); the same
variable also sends `x-claude-code-request-class`, which then decides which
turns count as delegated in place of the agent-id rule above.

- A caller that sends no session header is routed statelessly, and a compaction
  flag on such a request counts for that turn alone.
- A `count_tokens` probe records nothing — Claude Code sends those with a
  history one turn behind, so a committing probe would let stale history drive
  the pin. Once a session is pinned, the probe and the turn that follows read the
  same pin and so reach the same tier; on an *unpinned* session the probe is
  scored from its own history and can land on a different tier than the turn
  after it.
- Pins survive a config reload, but a pin remembers the router table it was made
  under: edit one router and only its own pins are dropped.
- Pins expire after `session_ttl_seconds`. Nothing is persisted across restarts.
  The compaction latch clears with the pin that carries it — on that expiry, or
  when a reload changes the router table.

## What the client sees

The tier travels upstream and nowhere else. Responses report the id the client
asked for, so Claude Code's `/model` display and `--resume` model restoration
keep working:

```
POST /v1/messages   {"model": "claude-auto", ...}
  → upstream receives  {"model": "claude-opus-4-8", ...}
  → client receives    {"model": "claude-auto", ...}
```

Two response headers report the decision, so you do not have to infer it:

| Header | Value |
| :-- | :-- |
| `x-gateway-routed-model` | The target the router chose (`claude-opus-4-8`) |
| `x-gateway-route-source` | Why (`override`, `dimensions`, `sticky`, `no_signal`, `fall_open`) |

Those five are the labels shunt emits today. The scorer defines three more —
`ambiguous`, `llm-classifier`, and `capable_hold` — and none can reach a
response: shunt reports an inconclusive turn as `fall_open`, runs no judge, and
keeps its own session hysteresis instead of the scorer's.

Both are absent for a model id that has no router, so "routed to the efficient
tier" stays distinguishable from "not routed by a router at all". A
`count_tokens` probe is left unstamped: on a session that is not yet pinned it
scores its own one-turn-behind history, so its tier is not necessarily the tier
of the turn it is measuring.

`GET /routes` lists every configured router under `routers`, with both targets
and the tier its picker falls back to when no signal decides. Two counters,
`shunt.stage_router.decisions` and `shunt.stage_router.flips`, are exported when
you enable metrics; flips are counted separately because a tier change is the
expensive event, and the decision counter cannot distinguish a session that just
moved from one that was already there.

## Configure it

```toml
[[models]]
id = "claude-auto"                     # must begin with claude/anthropic to reach /model
display_name = "Auto (stage router)"

[models.stage_router]
capable_target = "claude-opus-4-8"
efficient_target = "claude-sonnet-4-6"
# picker = "efficient_first"
# confidence_threshold = 0.5
# recent_turn_window = 3
# min_dwell_turns = 3
# deescalate_threshold = 0.75
# session_ttl_seconds = 3600
```

Both targets are ordinary public model ids, so each resolves through the normal
routing ladder and keeps its own failover chain, account pool, adapter, `effort`,
and `service_tier`. A target that is itself a router is a startup error, so
resolution is one hop by construction.

Every key is documented in the
[configuration reference](/reference/configuration/). The design record, including
what was deliberately left out, is
[ADR-0004](https://github.com/pleaseai/shunt/blob/main/.please/docs/decisions/0004-content-aware-stage-router.md).

## Limits

- **No mid-turn escalation.** Once response headers are committed shunt does not
  replay a turn, so a tier chosen at the start of a turn serves all of it.
- **No LLM judge.** Inconclusive signals fall open to the picker default.
- **Out of scope for `[server.codex_endpoint]`**, which uses its own routing
  table.
